## 1. 交付物定义（"交付什么"必须唯一）

> 核心纪律：**Idensona 交付的是"连续性"，不是"功能"**。任何以"我们也有语音/也有表情/也能聊天"来定义交付物的表述都是错的——那些是生态里别人已经做好的。

### 1.1 交付物清单（三层，清晰对位架构 §6）

| 层 | 交付物 | 形态 | 客户拿到什么 |
|---|---|---|---|
| **D-1 内核** | Idensona Core（身份/状态/记忆/人格/关系/发展史/行为政策 + 10 红线 + 回放取证） | F1 SDK / F2 容器 / F3 云 API | **"同一个它"的能力**——可跨模型、跨设备、跨时间 |
| **D-2 接缝** | Seam Layer（S1/S2/S3 + 身份映射） | 随 D-1 交付 | **接上既有链路的能力**——不需要重做语音管线 |
| **D-3 量尺** | Eval Harness + Gold Set + 回放报告 + 审计导出 | 随 D-1 交付（CLI/CI） | **可证明的能力**——不是"我们说它记得"，而是"这里有一份可复现的报告" |
| **D-4 Infra** ★ | 容器编排包（Helm/compose，Lite/Standard/Full）+ 运维件 + 离线 License | 随 CH-B 交付 | **能自己跑起来并运维的能力** |
| **D-5 Demo/Verify** ★ | 演示件（A/B 对照）+ 验收件（E-A/E-B/E-C 报告） | 随 CH-C 交付 | **能卖、能签字的能力** |

### 1.1b 三条分发通道（2026-11-26 裁决：1A + 2C + 3C）

> 详细设计见 [`Idensona_部署与分发设计_v0.9.2.md`](Idensona_部署与分发设计_v0.9.2.md)。规格约束见 [`规格书 §7.5`](Idensona_产品规格说明书_v0.9.2.md)。

| 通道 | 卖什么 | 计费逻辑（待验证） | 运维 | 对应交付物 |
|---|---|---|---|---|
| **CH-A API（多租户云）** | 能力订阅 | 按实例数 / 按调用量 / 按存储 | 我们 | D-1 + D-2 + D-5 |
| **CH-B SDK + Infra** | SDK 许可 + 编排包 | 按设备出货量 / 年授权 / NRE | 客户 | D-1…D-4 |
| **CH-C Demo + Verify** | 不单独售卖，销售与验收必备 | 计入 CH-A/B 交付成本 | 我们交付、客户运行 | D-5 |

> **纪律 DS-1~DS-4**（规格书 §7.5）：共用同一内核代码｜授权校验不得引入数据出境（离线 License）｜Demo/Verify 禁用真实数据｜多租户隔离为硬门。

### 1.2 交付物**不包含**（明确排除，防误解）

| 不交付 | 归属 |
|---|---|
| 语音管线（VAD/ASR/TTS） | 客户自选：小智 xiaozhi-server / 其他 |
| 设备管理与控制台 | 客户自选：xiaozhi-server + manager / 自建 |
| 硬件与结构 | 硬件合作方 |
| 运动控制与物理安全 | 载体厂商（机器人栈） |
| 模型推理服务 | 云厂商 / 客户自建边缘 |
| 表情与音色渲染 | 前端 / TTS 厂商 |

> **一句话**：**Idensona 交付"记忆与身份的中枢"，其余都是生态件**。这一定义决定了商业模式的形态——我们卖的是"中枢授权/订阅"，不是整机。

## 2. 交付场景（五种，按"谁用"划分）

### 2.1 场景总览

| # | 场景 | 谁在用 Idensona | 交付形态 | 成熟度 |
|---|---|---|---|---|
| SC-1 | **整机验证场**（elderly-companion） | 本项目自己 | F2 容器（与 xiaozhi-server 同机） | ✅ 链路已验证，接缝待做 |
| SC-2 | **硬件厂嵌入式授权** | 硬件厂后端（RK 系列主控） | F1 SDK 或 F2 容器 | ⏳ 需 D9–D15 |
| SC-3 | **家庭网关/私有云** | 家庭内网一台设备 | F2 容器 | ⏳ 需 F2 加固 |
| SC-4 | **平台型 API 服务** | 第三方 App / SaaS | F3 引擎 | ⏳ 需多租户与 SLA |
| SC-5 | **开发者生态（开源核心）** | 独立开发者 / 小团队 | 开源 + 商业模块 | ⏳ 需开源策略定型 |

### 2.2 SC-1 整机验证场（elderly-companion）—— 当前唯一可交付场景

**定位**：**不是产品，是验证场**。用户明确："Idensona + Elderly-companion，就是通过构建 Idensona 的核心功能，通过 Elderly-companion 来验证。"

| 项 | 内容 |
|---|---|
| 交付内容 | Idensona F2 容器 + 三条接缝 + 一份连续性验证报告 |
| 验证什么 | ①跨模型连续性（云端大模型 ↔ 边缘小模型切换后人格/记忆不变）②长周期记忆与关系演化 ③10 红线在真实语音链路中生效 ④情绪模块在老人语音上的可用性 |
| 不验证什么 | 硬件可靠性、量产成本、真实用户留存（那是后续 dogfood） |
| 成功判据 | 接缝三条全通 + 一份可复现的"换模型后仍是同一个它"报告 |
| 风险 | 依赖 elderly-companion 硬件到位（R-09） |

> **这一场景的商业价值**：它是 **SC-2/SC-3 的"样板间"**——硬件厂看到"这台机器换了模型还是同一个它"，才会相信 SDK 授权值得买。

### 2.3 SC-2 硬件厂嵌入式授权（主战场）

**客户画像**：已有整机产品（陪伴机器人/智能音箱/桌面宠物）但**缺"长期陪伴感"**的硬件厂。

**痛点（他们的原话通常是这样）**：
- "用户用两周就不玩了"——**新鲜感衰减**；
- "换个模型就得重新调人格"——**模型耦合**；
- "用户说它不记得我"——**无长期记忆**；
- "不敢让它乱说话"——**无合规护栏**。

**Idensona 提供的价值对位**：

| 他们的痛点 | Idensona 模块 | 可验证证据 |
|---|---|---|
| 新鲜感衰减 | 关系动力学 + 发展史 + 状态演化 | 关系得分曲线 + 回放报告 |
| 模型耦合 | Model Gateway 实例级切换 + 人格契约冻结 | 换模型前后断言零变化的报告 |
| 无长期记忆 | Memory OS 双时态 + 可控遗忘 | 记忆准确率 + 冲突治理报告 |
| 合规护栏 | 10 红线 + 审批留痕 + 审计导出 | 违规拒绝率 + `PolicyDecision` 全量留痕 |

**合作模式（三种，按侵入度递增）**：

| 模式 | 说明 | 客户改动 | 计费逻辑（待验证） |
|---|---|---|---|
| M-2a 云侧接入 | 客户的设备继续连自己的云，云的 LLM 调用指向 Idensona F3 | 后端改一个 endpoint | 按调用量/按实例订阅 |
| M-2b 边缘嵌入 | Idensona F1 SDK 装进客户主控（RK 系列） | 主控集成 SDK + sqlite | 按设备出货量授权 |
| M-2c 深度定制 | Idensona + 客户链路共同调优（如情绪模型定制） | 联合开发 | NRE + 授权 |

**前置条件**（诚实列出，缺一不可）：D9（S1 接缝）、D10（S2）、D11（身份映射）、D14（F1 SDK）。

### 2.4 SC-3 家庭网关 / 私有云

**定位**：面向**隐私敏感**客户（老人家庭、医疗陪护、特殊教育）——数据不出家门。

| 项 | 内容 |
|---|---|
| 交付 | F2 容器（含 PostgreSQL + pgvector）+ 一键部署脚本 |
| 卖点 | "记忆只在你家"——对齐隐私封闭纪律 |
| 与 SC-2 区别 | SC-2 卖给厂（B2B），SC-3 可卖给**服务商或高端家庭**（B2B2C） |
| 前置条件 | F2 加固（备份/恢复/升级）+ 出云窄门（可选云增强） |
| 风险 | 家庭运维能力弱（升级失败=数据风险）→ 需 A/B 升级与回滚设计 |

### 2.5 SC-4 平台型 API 服务

**定位**：把 Idensona 作为"记忆与身份中间件"卖给 App/SaaS 开发者。

**特点**：最轻资产，但**最重工程**（多租户隔离、SLA、计费、配额）。

**裁决已修订（2026-11-26）**：**SC-4 升级为 CH-A 主通道之一，列入交付范围**（用户裁决 1A 多租户云）。原"不优先"理由（对齐架构 X8 排除多租户）**已失效**——X8 已修订（微服务仍不做，多租户与编排已纳入）。
**保留的诚实声明**：仍**缺少一手客户需求证据**（目前无客户访谈记录）——因此 CH-A 的建设顺序为：先完成 tenant 隔离与配额（工程必修），**获客与定价仍待 T-04 访谈验证**。

### 2.6 SC-5 开发者生态（开源核心）

| 项 | 设计 |
|---|---|
| 开源什么 | **内核 + 接缝 + 量尺全部开源**（MIT/Apache-2.0 兼容）——因为"连续性"的价值在于被信任，闭源反而降低可信度 |
| 商业什么 | 托管服务（SC-3/SC-4）、企业支持、定制（SC-2c）、认证与合规包 |
| 为什么 | 生态定位要求"可被任何人验证"；开源是最低成本的信任建立方式 |
| 风险 | 竞品可直接抄内核——**但抄不走"验证报告与合规包"**（这是护城河所在，见 §4.2） |

> **注意**：开源策略涉及许可证选择（需 ADR），本文件不预设具体许可证。

## 3. 商业模式（四条候选路径，供决策）

> 用户要求："我不替你定——给出候选路径，各自前置条件与红海/蓝海定位。"

### 3.1 四条路径对照

| # | 路径 | 收入形态 | 前置条件 | 竞争强度（定性） | 现金流速度 |
|---|---|---|---|---|---|
| **P-1** | **整机 OEM 合作**（与硬件厂分成） | 整机毛利分成 / 每台授权 | 整机验证场跑通 + 一家愿意合作的厂 | 🔴 红海（硬件卷） | 慢（周期长） |
| **P-2** | **SDK / 记忆引擎授权** | 按设备出货量或年授权 | D9–D15 完成 + 样板间 | 🟡 蓝海偏中性（有 Mem0/Letta 但均非"连续性"定位） | 中 |
| **P-3** | **云订阅（记忆与身份服务）** | 月/年订阅（按实例） | F3 多租户 + SLA + 合规 | 🟡 蓝海（消费级"身份连续性"订阅罕见） | 快（但需获客） |
| **P-4** | **开源核心 + 商业记忆引擎/合规包** | 企业支持 + 合规认证 + 定制 | 开源策略定型 + 社区 | 🟢 蓝海（"可验证的连续性"无人做） | 最慢（信任积累） |

### 3.2 各路径的前置条件清单（可执行）

| 路径 | 技术前置 | 商业前置 | 合规前置 |
|---|---|---|---|
| P-1 | SC-1 验证场通过 | 找到 1 家 OEM 试点 | 整机责任划分（安全归厂） |
| P-2 | D9–D15 全通；F1 SDK 稳定 | 2–3 家厂 PoC | SDK 授权条款 |
| P-3 | F3 多租户 + 99.5% SLA 设计 | 获客渠道（内容/开发者） | 数据出境与属地存储 |
| P-4 | 开源仓库门面 + 文档 | 社区运营投入 | 开源许可证 ADR |

### 3.3 推荐组合（本项目判断，可争论）

> **判断依据**：技术成熟度（内核已完整、接缝未做）+ 现金流需求（不确定）+ 竞争位置（"连续性"是空白）。

**推荐：P-2 为主线，P-1 为验证，P-3/P-4 为后续。**

```
阶段 1（现在–接缝完成）：SC-1 验证场（不赚钱，赚证据）
        ↓ 拿到"换模型仍是同一个它"的可复现报告
阶段 2：P-2 SDK 授权（找 2–3 家硬件厂 PoC）＋ P-1 的 OEM 试点（一家）
        ↓ 拿到首批付费合同 + 真实出货数据
阶段 3（视情况）：P-3 云订阅（若 C 端获客渠道成立）｜P-4 开源社区（若品牌需要）
```

**为什么不以 P-1 为主线**：整机是红海（硬件毛利低、周期长、需供应链能力），而 Idensona 的护城河在软件——把力量放在硬件分成上会稀释核心优势。

**为什么不以 P-3 为主线（现在）**：F3 多租户工程量大，且**当前无一手客户需求证据**；先做 B 端授权更符合"技术已验证、商业未验证"的现状。

## 4. 红海 / 蓝海定位（按功能类型区分）

> **数据纪律**：本节全部为**定性判断**（"红海/蓝海"指功能供给密度与差异化空间），**不含任何市场份额数字**。竞品名单见 [`Idensona_竞品与市场分析_v0.9.2.md`](Idensona_竞品与市场分析_v0.9.2.md)。

### 4.1 功能级红蓝海矩阵

| 功能 | 供给密度 | 定位 | 我们的策略 |
|---|---|---|---|
| 语音唤醒 / ASR / TTS | **极高**（芯片厂免费给、云厂白菜价） | 🔴 **红海** | **不做**（用 xiaozhi 等现成） |
| 通用聊天 / 人格人设 | **极高**（Character.AI 类 + 各模型自带） | 🔴 **红海** | 不做（用模型 + 人格契约） |
| 设备管理 / 配网 / OTA | **极高**（小智生态已成熟） | 🔴 **红海** | 不做（用 xiaozhi-server） |
| 表情 / 视觉形象 | **高**（各硬件厂自研） | 🔴 **红海** | 不做（前端决定） |
| 情绪**识别**（声学/文本） | **中高**（学术界成熟、有开源模型） | 🟡 **偏红** | **只做"进入状态"那一段**（不拼识别精度） |
| 通用 Agent 记忆（RAG/向量） | **高**（Mem0/Letta/Zep 等） | 🔴 **红海** | 不做通用记忆；做**双时态 + 冲突治理**的差异化 |
| **跨模型身份连续性** | **极低**（未见成熟生产实现） | 🟢 **蓝海** | **主攻**（核心护城河） |
| **可回放 / 可取证的状态演化** | **极低** | 🟢 **蓝海** | **主攻** |
| **依恋安全护栏（10 红线 + 审批留痕）** | **低**（有通用 guardrail，无依恋专项） | 🟢 **蓝海** | **主攻** |
| **情绪 → 长期状态的可回放映射** | **极低** | 🟢 **蓝海** | **主攻**（Emotion 模块的差异化点） |
| **身份可携带（实例导出/迁移）** | **低** | 🟢 **蓝海** | 中期（D15） |

### 4.2 护城河的三个支柱（为什么抄不走）

| 支柱 | 内容 | 为什么难抄 |
|---|---|---|
| **H-1 协议与 provenance 粒度** | 每条 L1 事件携带模型/提示/代码版本，使重放确定性成立 | 要在架构第一天就设计，后补成本极高 |
| **H-2 验证资产** | Gold Set + 四臂基线 + 回放报告 + 盲测协议 | 是"长期积累型资源"，无法速成 |
| **H-3 合规包** | 多法域 Consent + 两级删除 + 审计导出 | 需要真实法务与流程投入 |

> **注意**：护城河**不在代码复杂度**（Python + PostgreSQL 并不难写），而在 **H-1 的设计纪律 + H-2 的积累 + H-3 的合规投入**。这是"为什么大厂不做"的答案：他们能做代码，但不愿为"长期身份"承担验证与合规成本。

### 4.3 红海的正确用法：把它们变成"交付起点"

| 红海能力 | 我们如何用 |
|---|---|
| 小智语音链路 | **直接接入**（S1/S2/S3），零自研成本 |
| 云模型 / 边缘模型 | **Provider 注册表**，随时换 |
| 智控台 | 直接复用（设备/用户/模型配置） |

> **战略含义**：**红海能力越成熟，Idensona 的启动成本越低**——我们不需要重建生态，只需成为生态的"中枢"。

## 5. 客户画像（B 端优先，C 端暂缓）

### 5.1 B 端画像（SC-2/SC-3 的目标客户）

| 维度 | 特征 |
|---|---|
| 类型 | 消费级机器人/陪伴硬件厂（已有产品在售，缺"陪伴感"） |
| 规模（定性） | 中小厂为主（大厂自研意愿强，中小厂更愿买授权） |
| 决策人 | 产品负责人 + CTO（技术可行性 + 差异化卖点） |
| 关键顾虑 | ①集成成本 ②数据合规责任 ③"能不能证明有效" |
| 我们的应答 | ①三条接缝（不是重写）②审计导出与出境窄门 ③H-2 验证资产 |

### 5.2 C 端画像（SC-3 高端家庭，暂缓）

| 维度 | 特征 |
|---|---|
| 类型 | 老人家庭（子女付费）/ 特殊教育 / 医疗陪护 |
| 付费意愿（定性） | 高（为"陪伴质量"付费的动机强于"功能数量"） |
| 障碍 | 安装运维能力弱、隐私顾虑重、对"机器记得我"的不安 |
| 我们的应答 | 一键部署 + "记忆只在你家" + 擦除可验证 |

> **诚实声明**：以上画像为**基于产品逻辑的推断**，**尚未经客户访谈验证**。验证方式见阶段文档的 T-04（客户访谈）。

## 6. 商业风险

## 8. 一句话总结

**Idensona 卖的是"连续性"这条软件能力的授权与托管——它必须依赖成熟生态（语音、模型、硬件）才能发挥价值，因此商业上应做"中枢"而非"整机"；四条路径中，SDK 授权（P-2）与整机 OEM 验证（P-1）是当前唯一有证据支撑的组合，云订阅与开源生态留待客户证据出现后再启动。**
