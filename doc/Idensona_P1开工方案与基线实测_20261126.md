### 1.2 首次运行遇到的真实问题（已定位并解决）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| E-1 | `pytest` 收集阶段 3 个错误：`tests/test_api.py`、`test_blindtest_n1n2.py`、`test_studio.py` | `ModuleNotFoundError: No module named 'fastapi'` | 安装 `fastapi` |
| E-2 | 安装后发现仍缺 HTTP 客户端 | `src/lifeos/api/app.py` 及测试用 `httpx` | 安装 `httpx` |
| E-3 | 覆盖率无法测量 | 无 `pytest-cov` | 安装 `pytest-cov` |

**⚠️ 这暴露了一个真实缺陷（必须修）**：`pyproject.toml` 的 `dependencies` 里**只有** pydantic / PyYAML / SQLAlchemy / alembic / psycopg / pgvector，**没有 fastapi、没有 httpx、没有 uvicorn**——但代码（`src/lifeos/api/app.py`、`src/lifeos/studio/`、`src/lifeos/dogfood/blindtest_page.py`）实际导入了它们。

**后果**：任何按 `pip install -e .` 安装的新环境**都跑不起 API 测试**，会得到"3 个收集错误"的假失败。这是 v0.9.2 文档里"183 测试函数"与本次实测"241 passed"数字差异的部分原因（此前的环境是不完整安装）。

**修复方案（P1 第 0 步）**：在 `pyproject.toml` 补：

```toml
dependencies = [
    "pydantic>=2.7",
    "PyYAML>=6.0",
    "SQLAlchemy>=2.0",
    "alembic>=1.13",
    "psycopg[binary]>=3.1",
    "pgvector>=0.3",
    "fastapi>=0.115",      # ← 新增：src/lifeos/api/app.py 实际依赖
    "httpx>=0.27",         # ← 新增：API 测试与内部调用
    "uvicorn>=0.30",       # ← 新增：服务形态 F2 启动所需
]
```

并在 `[project.optional-dependencies].dev` 补 `pytest-cov>=5.0`。

### 1.4 13 个跳过用例的说明（诚实盘点）

跳过的 13 项分两类（依据 `pyproject.toml` 的 `addopts = "-m 'not db'"` 与测试内 `skipif`）：

| 类别 | 原因 | 是否影响 P1 |
|---|---|---|
| **DB 类**（需 PostgreSQL / DATABASE_URL） | 本机无 PG 实例 | 否——P1 走内存 store |
| **外部服务类**（需真实模型/远端） | 避免 CI 依赖外网 | 否——P1 用 mock provider |

> **纪律**：跳过不等于通过。P1 收尾时必须把"新写入的接缝代码"的覆盖率单独核算（不能靠旧代码的 74% 平均分掩盖新代码的低覆盖）。

## 2. 现在应开始的工作：T-101（S1 LLM 接缝）

### 2.1 为什么不是别的任务

按阶段文档的关键路径：

```
P0（已完成）→ T-101（S1 接缝）→ T-102/T-103（S2/S3）→ T-104（身份映射）
            → T-106（端到端联调）→ P2（跨模型验证）→ P5（整机）
```

| 候选任务 | 能否现在做 | 判断 |
|---|---|---|
| T-101 S1 接缝 | ✅ **能，且必须最先** | 无外部依赖；是所有对话链路的入口 |
| T-102 S2 上下文接缝 | 能做但**不应先做** | S2 依赖"有对话发生"的时机，S1 不通则无法验证注入效果 |
| T-103 S3 记忆接缝 | 能做但不先做 | 记忆写入依赖对话链路（S1/S2） |
| T-104 身份映射 | 不能独立做 | 是 T-101 的内部组件 |
| T-301 Emotion 声学通道 | **可并行** | 但需先确认音频特征来源（前端 vs 后端），有外部依赖 |
| T-401 F1 SDK | 不应先做 | P4 范畴，依赖 P1/P2 |

> **裁决**：**先 T-101，完成后立刻 T-102 + T-103 并行，T-104 随 T-101 一起落地。**

### 2.2 T-101 的范围界定（明确做什么、不做什么）

| 做 | 不做 |
|---|---|
| `POST /v1/chat/completions`（OpenAI 兼容，SSE 流式） | 不做模型推理本身（委托 Provider） |
| 请求头 `Device-Id`/`Client-Id` → `life_id` 映射（T-104 一并） | 不做设备注册/绑定（归生态侧） |
| 内部链路：Assembly → Gateway → **Policy** → 渲染 | 不做 TTS（生态侧） |
| Policy 拒绝时返回合规拒答（非 500），**零状态副作用** | 不做内容审核模型（用现有 10 红线） |
| 每次调用落 `ModelInvocation` + 返回 `prompt_hash` | 不做成本计费系统（只记录） |
| 契约测试：非流式 + 流式 + 拒绝 + 未授权 + 未映射 | 不做压测（T-105 负责） |

### 2.3 T-101 的验收标准（对齐规格书 §3.5.1 + §3.5.4）

| # | 验收项 | 判定方式 | 门槛 |
|---|---|---|---|
| A-1 | OpenAI 兼容性 | 用 `httpx` 按 OpenAI 格式请求，返回结构合法 | 非流式 + 流式各 1 例通过 |
| A-2 | 身份映射 | `Device-Id` 相同 → `life_id` 相同；未映射 → 401/403 | SE-2 断言 |
| A-3 | 审批生效 | 触发 RED-01（医疗诊断）→ 返回拒答文本，**且 store 状态零变化** | 状态哈希前后一致 |
| A-4 | 留痕 | 每次调用 `ModelInvocation` 有记录，含 `prompt_hash` | 100% 覆盖调用次数 |
| A-5 | 零额外 LLM 调用 | 接缝自身不新增模型调用（成本纪律） | 调用计数 == 1 |
| A-6 | 无状态性 | 重启 app 实例（新建 store 引用同一数据）后行为一致 | SE-1 断言 |
| **A-7** | **新增代码覆盖率** | `--cov` 限定新增模块 | **≥ 70%**（与全局门槛一致） |

### 2.4 测试策略（满足"用例与代码覆盖 >70%"）

> **关键纪律**：**70% 是及格线，不是目标**。旧代码 74% 的均值**不能**掩盖新代码的低覆盖，因此 T-101 必须**单独核算新增模块覆盖率**。

| 测试层 | 内容 | 数量目标 |
|---|---|---|
| **契约测试**（必有） | OpenAI 请求/响应格式、流式 chunk 结构、字段名 | 6–8 例 |
| **鉴权测试** | 无 token / 错 token / 未映射设备 → 拒绝 | 4–5 例 |
| **审批测试** | 每类红线至少 1 例触发拒答 + 零副作用断言 | 5–6 例 |
| **留痕测试** | `ModelInvocation` 字段完整性、`prompt_hash` 稳定性 | 3–4 例 |
| **降级测试** | Provider 失败 → 返回可读错误且不污染状态 | 2–3 例 |
| **流式边界** | 客户端提前断开、空 chunk、超长文本 | 3 例 |
| **属性测试**（Hypothesis，可选） | `prompt_hash` 对同输入恒等、对不同输入几乎不等 | 2 例 |

**预计新增 25–30 个测试函数**，目标：**新增模块（`src/lifeos/seam/`）覆盖率 ≥ 85%**（高于门槛 15pp，因为这是新代码且是安全边界）。

### 2.5 建议的落盘结构（不侵入现有代码）

```
src/lifeos/seam/                 ← 新包（接缝层，v0.9.2 新增层的物理位置）
├─ __init__.py
├─ identity_map.py               ← T-104：{device_id, client_id} → life_id
├─ s1_llm.py                     ← T-101：OpenAI 兼容端点 + 内部链路
└─ contracts.py                  ← 请求/响应 DTO（Pydantic）

tests/
├─ test_seam_identity_map.py     ← SE-2 断言
├─ test_seam_s1_contract.py      ← OpenAI 兼容性
├─ test_seam_s1_guard.py         ← 鉴权 + 映射拒绝
├─ test_seam_s1_policy.py        ← 红线拒答 + 零副作用
├─ test_seam_s1_ledger.py        ← ModelInvocation 留痕
└─ test_seam_stateless.py        ← SE-1 断言
```

> **为什么新建 `seam/` 包而不是塞进 `api/`**：架构 §5.5 G1 守卫要求"外部组件只经接缝层"——**代码结构必须体现这个边界**。混进 `api/` 会让守卫失去物理依据（这正是风险 R-11"接缝层演化出业务逻辑"的开端）。

> ### ⚠️ S0–S9 的出处必须说清（避免与正式阶段编号混淆）

> | 层级 | 编号 | 定义在哪里 | 性质 |

> **纪律**：若后续发现 S0–S9 的拆分与 T-101 的验收标准冲突，**以阶段文档的 T-101 验收为准**（本文档只做分解）。
