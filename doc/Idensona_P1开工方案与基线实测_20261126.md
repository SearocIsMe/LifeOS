### 1.2 首次运行遇到的真实问题（已定位并解决）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| E-1 | `pytest` 收集阶段 3 个错误：`tests/test_api.py`、`test_blindtest_n1n2.py`、`test_studio.py` | `ModuleNotFoundError: No module named 'fastapi'` | 安装 `fastapi` |
| E-2 | 安装后发现仍缺 HTTP 客户端 | `src/lifeos/api/app.py` 及测试用 `httpx` | 安装 `httpx` |
| E-3 | 覆盖率无法测量 | 无 `pytest-cov` | 安装 `pytest-cov` |

**⚠️ 这暴露了一个真实缺陷（必须修）**：`pyproject.toml` 的 `dependencies` 里**只有** pydantic / PyYAML / SQLAlchemy / alembic / psycopg / pgvector，**没有 fastapi、没有 httpx、没有 uvicorn**——但代码（`src/lifeos/api/app.py`、`src/lifeos/studio/`、`src/lifeos/dogfood/blindtest_page.py`）实际导入了它们。

**后果**：任何按 `pip install -e .` 安装的新环境**都跑不起 API 测试**，会得到"3 个收集错误"的假失败。这是 v0.9.2 文档里"183 测试函数"与本次实测"241 passed"数字差异的部分原因（此前的环境是不完整安装）。

**修复方案（P1 第 0 步）**：在 `pyproject.toml` 补：

```toml
dependencies = [
    "pydantic>=2.7",
    "PyYAML>=6.0",
    "SQLAlchemy>=2.0",
    "alembic>=1.13",
    "psycopg[binary]>=3.1",
    "pgvector>=0.3",
    "fastapi>=0.115",      # ← 新增：src/lifeos/api/app.py 实际依赖
    "httpx>=0.27",         # ← 新增：API 测试与内部调用
    "uvicorn>=0.30",       # ← 新增：服务形态 F2 启动所需
]
```

并在 `[project.optional-dependencies].dev` 补 `pytest-cov>=5.0`。

### 1.4 13 个跳过用例的说明（诚实盘点）

跳过的 13 项分两类（依据 `pyproject.toml` 的 `addopts = "-m 'not db'"` 与测试内 `skipif`）：

| 类别 | 原因 | 是否影响 P1 |
|---|---|---|
| **DB 类**（需 PostgreSQL / DATABASE_URL） | 本机无 PG 实例 | 否——P1 走内存 store |
| **外部服务类**（需真实模型/远端） | 避免 CI 依赖外网 | 否——P1 用 mock provider |

> **纪律**：跳过不等于通过。P1 收尾时必须把"新写入的接缝代码"的覆盖率单独核算（不能靠旧代码的 74% 平均分掩盖新代码的低覆盖）。

## 2. 现在应开始的工作：T-101（S1 LLM 接缝）

### 2.1 为什么不是别的任务

按阶段文档的关键路径：

```
P0（已完成）→ T-101（S1 接缝）→ T-102/T-103（S2/S3）→ T-104（身份映射）
            → T-106（端到端联调）→ P2（跨模型验证）→ P5（整机）
```

| 候选任务 | 能否现在做 | 判断 |
|---|---|---|
| T-101 S1 接缝 | ✅ **能，且必须最先** | 无外部依赖；是所有对话链路的入口 |
| T-102 S2 上下文接缝 | 能做但**不应先做** | S2 依赖"有对话发生"的时机，S1 不通则无法验证注入效果 |
| T-103 S3 记忆接缝 | 能做但不先做 | 记忆写入依赖对话链路（S1/S2） |
| T-104 身份映射 | 不能独立做 | 是 T-101 的内部组件 |
| T-301 Emotion 声学通道 | **可并行** | 但需先确认音频特征来源（前端 vs 后端），有外部依赖 |
| T-401 F1 SDK | 不应先做 | P4 范畴，依赖 P1/P2 |

> **裁决（2026-11-27 修订）**：**先做 P1-PRE-1 / P1-PRE-2 两道前置 → 再做 T-101（含 T-104 身份映射）→ 完成后 T-102 + T-103 并行**。
> **原裁决的问题**：原方案直接开 T-101，未考虑多租户决策——接缝函数若先不带 `tenant_id`，P6 时要全部改签名 + 改测试（返工）。**先打抽象、后写功能**，顺序不能倒。

### 2.4 测试策略（满足"用例与代码覆盖 >70%"）

> **关键纪律**：**70% 是及格线，不是目标**。旧代码 74% 的均值**不能**掩盖新代码的低覆盖，因此 T-101 必须**单独核算新增模块覆盖率**。

| 测试层 | 内容 | 数量目标 |
|---|---|---|
| **契约测试**（必有） | OpenAI 请求/响应格式、流式 chunk 结构、字段名 | 6–8 例 |
| **鉴权测试** | 无 token / 错 token / 未映射设备 → 拒绝 | 4–5 例 |
| **审批测试** | 每类红线至少 1 例触发拒答 + 零副作用断言 | 5–6 例 |
| **留痕测试** | `ModelInvocation` 字段完整性、`prompt_hash` 稳定性、**含 `tenant_id`** | 4–5 例 |
| **降级测试** | Provider 失败 → 返回可读错误且不污染状态 | 2–3 例 |
| **流式边界** | 客户端提前断开、空 chunk、超长文本 | 3 例 |
| **属性测试**（Hypothesis，可选） | `prompt_hash` 对同输入恒等、对不同输入几乎不等 | 2 例 |
| **租户隔离测试** ★新增 | 跨 tenant 越权（读/写/留痕）全端点覆盖 | **6–8 例** |
| **请求上下文测试** ★新增 | `RequestContext` 贯穿（不可变、默认 tenant、缺失报错） | 3–4 例 |

**预计新增 33–40 个测试函数**（原 25–30 + 租户相关 9–12），目标：**新增模块（`src/lifeos/seam/` 与 `src/lifeos/context.py`）覆盖率 ≥ 85%**（高于门槛 15pp，因为这是新代码且是安全边界）。

> **覆盖率核算方式（必须按此执行，防"平均值掩盖"）**：
> ```bash

> python -m pytest tests/test_seam_*.py tests/test_context*.py \
>   --cov=lifeos.seam --cov=lifeos.context --cov-report=term-missing
> ```

## 4. 三项决策（**已于 2026-11-27 由项目负责人确认，生效**）

> 以下三项为**受控决策**，实现中须写成常量并附注释（标注"可变更点 + 变更须走 ADR"）。

| # | 决策 | **确认结果** | 影响面 | 落地位置 |
|---|---|---|---|---|
| **Q-1** | **`life_id` 映射策略** | **① 设备绑定唯一 `life_id`** | `identity_map.py` 主键为 `(tenant_id, device_id, client_id)`；一个设备恒对应一个 Instance | `src/lifeos/seam/identity_map.py`；常量 `MAPPING_STRATEGY = "device_bound_single"` |
| **Q-2** | **Policy 拒答返回内容** | **① 固定模板（确定性、可测试）** | 拒答文本为常量模板，**不含任何 LLM 生成**；保证"拒答"本身可回放 | `MAPPING_STRATEGY` 旁：`REFUSAL_TEMPLATE_ID = "refusal.fixed.v1"`；模板存版本化资源 |
| **Q-3** | **Provider 未配置行为** | **① fail-closed 报错** | 未配置 Provider → 抛 `GatewayError`（不回落、不 mock） | 复用 [`gateway/provider.py:18-19`](../src/lifeos/gateway/provider.py:18) 现有 `GatewayError` |

**Q-1 的一个重要补充约束（我按决策语义补的，请确认）**：
- 选"设备绑定唯一 `life_id`"意味着：**家属作为次用户不新建 Instance，而是同一 Instance 下的另一个 `subject_id`**（对齐架构 §6.4 四层标识：Tenant → Instance → Subject）。
- 这保持 P0 已有的"老人=A subject、家属=B subject，跨 subject 召回必为空"能力，**无需改数据模型**。
- 若将来需要"同一设备切换主用户"（如设备转赠），须走 **F11 导出/导入 + 映射表变更留痕**，不得原地改映射。

**Q-2 的一个诚实提醒**：固定模板意味着**拒答话术不能因人/因情境变化**（例如老人 vs 家属听到的拒答措辞相同）。这是**确定性换来的代价**，也是可回放的必然要求。若将来要在"拒答措辞"上做个性化，必须走 ADR 并接受"拒答不可回放"的后果。

**Q-3 的一个连带影响**：fail-closed 意味着**首次部署若 Provider 未配，接缝会直接报错**——这对客户是"配置不完整"的明确信号（好事），但**部署文档必须显著提示**（否则客户会误以为服务坏了）。已记入 P4 的部署手册要求。
