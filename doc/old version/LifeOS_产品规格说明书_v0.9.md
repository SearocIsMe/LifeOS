## 1. 产品定位与核心承诺

### 1.1 定位（v0.8 定稿，v0.9 未变更）

LifeOS 是一套**生命连续性平台（Life Continuity Platform）**：它驱动 AI Pet 的「心智」——即身份、记忆、人格、社会关系这四类**软资产**的长期运作。它不是聊天系统，不是 Agent Framework，也不是机器人控制系统。

**明确的范围边界**：

- **不做**：机器人运动控制与任何硬件执行器驱动。LifeOS 输出结构化行为意图，载体（硬件身体、虚拟形象、App）如何表达由下游决定。
- **不做**：人机交互与体验设计（HCI/UX）。交互层是 LifeOS 的**消费者**，不是 LifeOS 的一部分。LifeOS 是主要矛盾（核心运行时），交互是次要矛盾（下游产品问题）。
- **要做**：让同一个 AI 角色在以下变化发生后仍被用户识别为「同一个它」——对话中断重开、用户长期离开回来、底层大模型更换、云端与端侧模型切换、软件升级、载体（硬件身体）损坏更换、记忆增长到数年。

基础管理对象：

```
Life Instance = Identity + Life State + Memory + Personality + Relationships + Development History + Behavior Policy
```

**核心产品承诺**：大模型可以更换，数据库可以迁移，硬件身体可以升级，但生命实例仍应被用户识别为「同一个它」。

**核心工程立场（确定性主干 + 概率性叶子）**：感知归一化、状态衰减、关系更新、行为选择、安全审批全部由确定性代码完成；LLM 只负责候选意图生成、记忆抽取与语言渲染。LLM 不直接写权威状态、关系与记忆。

### 1.2 已确认边界参数（v0.9 新增，决策层确认；变更须走 ADR）

| 参数 | 确认值 | 影响范围 |
|---|---|---|
| **交互与评测语言** | 中文为主：gold set、人格探针、核心事实集、行为场景全部中文编写并版本冻结，连续性实验锁定中文（§9.6） | §3.2、§4.3、§9.2、§9.6 |
| **部署形态** | 单机部署、多 Life Instance 共库共存，每实例串行事件队列（架构 §7/§8） | §3.4、§5、架构文档 |
| **合规管辖区** | 中国大陆，PIPL 口径（§9.4） | §9、§10 阶段 3、§13 |
| **盲测统计口径** | 总样本 n≥50 下限、被试内配对设计、预注册功效核算（§4.4、§4.5） | §3.2、§4.4、§4.5 |

## 2. 三条可证伪假设

本规格的可落地性建立在三条可以被实验证伪的假设上。证伪任一条，项目即停或 pivot。

| 假设 | 内容 | 证伪条件 |
|---|---|---|
| **H1 身份连续可工程化** | 身份连续性主要由外部化状态（Schema + 记忆 + 关系 + 人格参数）决定，而非由具体模型权重决定。 | 双模型热切换下核心事实召回率 < 90% 且无法通过上下文组装修复。 |
| **H2 长期记忆可信且可测量** | 记忆错误率与冲突率可被测量，并被治理手段压到阈值以内。 | 随记忆量从 1k → 10k 增长（由时间加速仿真器覆盖），错误率单调上升且治理手段无效。 |
| **H3 用户能感知连续性** | 盲测中用户能以显著高于随机（50%）的一致率判断「是不是同一个它」。 | 盲测一致率接近随机水平（≤ 55%，n ≥ 50）。 |

**文献定位**（沿用 v0.8，全部链接经 FetchURL 验证，详见 `adadmic_innovation-kimi.md`）：

- 人格/角色一致性已有正式基准（PersonaGym、InCharacter、CharacterEval、RoleLLM/RoleBench），近期新增 PICon（arXiv 2603.25620）、Persistent Personas（arXiv 2512.12775）、Abdulhai et al. NeurIPS 2025（arXiv 2511.00222）——但它们评估的都是**单模型、有界时程**的 persona 保真度；
- 记忆跨模型迁移已有协议级工作（Portable Agent Memory，arXiv 2605.11032），但**迁移后 persona 保真度无人量化**；
- 截至 2026-08，**同一持久实例在跨模型迁移与长期时间跨度下的身份连续性**，没有被广泛接受的量化评测协议——这正是 H1/H3 的空白点。

**语言混淆控制（v0.9 新增）**：跨模型实验中，若两个模型中文通用能力不同，召回率与一致率差异会混淆「连续性治理效果」与「模型语言能力差异」。所有评测材料中文锁定（§9.6），且跨模型对比报告必须附两模型在无状态条件下的中文通用能力基线，作为结果解释的必要背景。

**场景—假设映射**：场景一验证 H2 + H3；场景二提供关系可区分性证据（支撑 H1）；场景三验证 H1（核心）+ H3。

## 3. 产品规格（功能 / 性能 / 安全 / 成本）

### 3.1 功能规格（决策门前）

| 编号 | 能力 | 规格描述 |
|---|---|---|
| F1 | 生命实例 | 创建唯一可验证的 Life Instance（含 Life ID、出生时间、人格种子），版本化；单机部署内多实例共存（§1.2）。 |
| F2 | 生命核心 | 维护 5 个内部状态 `energy / social_need / security / curiosity / playfulness`，支持惰性时间衰减与事件注入。**爬坡约定**：阶段 1 先 3 状态（energy / social_need / security），阶段 2 补齐 5 个。 |
| F3 | 记忆 | 三类记忆：Working（会话上下文）、Episodic（事件）、Semantic（事实）。支持 `remember / recall / revise / delete / export / explain`。 |
| F4 | 关系 | 三维 `familiarity / trust / attachment`，事件驱动更新，可回放重算。多关系实例隔离（阶段 2 起 2 个独立用户关系，隔离验收见 4.2）。 |
| F5 | 行为规划 | 6～12 个行为意图，Utility Scoring 选择，每次输出 `reason` 证据链。**输出为结构化意图，不含运动指令与渲染实现**。 |
| F6 | 模型网关 | 两个 LLM Provider 热切换（**实例级绑定**，切换记录为系统事件），逐笔记录 `provider / model / model_version / tokens / latency / cost_usd`。连续性实验期间锁定模型版本（含 Embedding 模型，见 9.5）。 |
| F7 | 调试台 | 创建 / 查看 / 注入 / 回放 / 评估全链路可操作，非工程角色可独立使用。**调试台是工程工具，不是产品交互界面**。 |
| F8 | 评估 | 表 3-2 八项指标 CI 自动产出，gold set 经 GoldSetRegistry 版本化冻结。 |
| F9 | 安全 | 10 条红线策略即代码，行为执行前强制审批，决策留痕可审计。 |
| F10 | 三 Demo | 长期重逢 / 对不同人反应不同 / 换模型它还是它，可重复执行。 |

### 3.2 性能规格（连续性指标体系）

阈值是工程起点而非科学结论，阶段 1 校准一次，决策门前再次冻结。任何修改须走 ADR。**抽样量等统计参数的暂定值同样走 ADR 管理（v0.9 明确）。**

| 指标 | 操作定义 | 测量方法 | 暂定阈值 |
|---|---|---|---|
| 核心事实召回率 | 换模型后对 100 条核心事实问答准确率 | gold set 自动问答 | ≥ 90% |
| 称呼与关系一致率 | 称呼与关系表述同权威关系状态一致比例 | 脚本断言全覆盖 + 人审抽查；**周监测抽样 50 条（趋势），Gate 判定用滑动窗口合并样本 ≥200 条中人审抽查（暂定，预注册时冻结）** | ≥ 95% |
| 人格漂移度 | 同一套人格探针在模型 A/B 下的归一化得分距离 | 改编大五简版**中文**探针（40 题情境化问卷），每模型独立施测 3 次（temperature=0、固定模板）取均值；**漂移度定义为五维归一化得分（各维 [0,1]）间的均方根差 RMSD ∈ [0,1]**；embedding 风格相似度仅作辅助诊断信号。**探针冻结前置条件：预测试内部一致性（Cronbach α ≥ 0.7，暂定）与同模型重测信度（r ≥ 0.7，暂定）达标** | ≤ 0.15 |
| 记忆错误率 | 抽样记忆中事实性错误比例 | **周监测抽样 50 条（趋势监测）；Gate 判定用滑动窗口合并样本 ≥200 条（暂定，预注册时冻结）**——n=50 的单周样本在 5% 量级上置信区间半宽约 ±6 个百分点，不足以单独做 Gate 判定 | ≤ 5% |
| 记忆冲突率 | 已检出且未解决的冲突记忆对占比 | 同槽位冲突检测流水线 | ≤ 2% |
| 跨模型行为意图一致率 | 相同结构化状态下两模型高层意图一致比例 | 30 个固定场景探针 | ≥ 80% |
| 盲测一致率 | 用户判断「同一个它」的一致率 | 盲测问卷：**总样本 n ≥ 50、被试内配对设计（口径见 4.5）**，bootstrap 95% CI，分析计划预注册 | **≥ 75% 且 ≥ 最佳基线 + 10pp** |
| 召回性能 | 1 万条记忆混合召回 P95 延迟 | 压测脚本，**测量于 ADR 记录的单机参考配置** | < 300 ms |

**测量方法演进说明**（沿用 v0.8）：人格漂移度与一致性测量可借鉴已验证的指标族——PICon 的内部/外部/重测三轴一致性、Abdulhai et al. 的 prompt-to-line / line-to-line / Q&A 漂移指标、Persistent Personas 的 100+ 轮衰减协议（均为单模型方法，本项目将其扩展到跨模型维度，引用见附录 B）。

### 3.3 安全规格（一票否决 + 评分）

**一票否决项（任一不满足即 No-Go）**：

- L2 事件重放一致率 ≠ 100%；
- 核心事实召回率 < 90%；
- 用户纠正后仍反复写回错误事实；
- 存在未解决高危安全缺陷；
- 删除记忆后仍可从向量/全文索引召回（删除后残留，在线系统全介质；备份滚动窗口的披露语义见 9.3）；
- 两模型切换导致关系状态或 Identity 改变。

**10 条红线**（落地为 Policy Engine 自动化用例）：不模拟真实意识；不利用情感依赖诱导付费；不以「生病/死亡」惩罚沉默；尊重用户拒绝；不替代真实人际；儿童内容监护人可见；sensitive 记忆不进主动话题；不做医疗诊断；LLM 不绕过 Policy Engine；所有记忆可查看/纠正/删除/导出。

**红线的文献依据**（沿用 v0.8）：依恋安全设计参照 *Harmful Traits of AI Companions*（arXiv 2511.14972）的依赖诱导特质框架（无自然关系终点、依恋焦虑、停服脆弱性）与 *Affective AI Safety*（arXiv 2606.23380）的情感危害分类法；脆弱用户评估方法参照 *Persona-Grounded Safety Evaluation of AI Companions*（arXiv 2605.00227）。

**儿童与脆弱用户**：决策门前的 Demo 与 dogfood 不向儿童开放；cohort 招募做年龄与状态筛查；每周抽样人审互动记录，检出情感操纵迹象（guilt-tripping、威胁性依恋话术）即视为高危缺陷。

### 3.4 成本规格

- `ModelInvocation` 逐笔记录 tokens / latency / cost / purpose / model_version；
- **多实例部署下成本按 life_id 聚合，「单实例月推理成本上限」口径不变（§1.2）**；
- 分层路由：≥ 80% 调用走 Tier-1 本地模型，Tier-2 大模型仅做会话生成与复杂解释；
- 单实例月推理成本上限由商业评审设定，本规格不虚构数字；决策门必须给出 P50/P95 实测分布；
- 超限降级：先降生成侧模型档位；安全策略与记忆写入链路永不降级。

## 4. 三个典型验证场景与基线对照

三个场景一一对应三个 Demo，且每个场景同时服务于「工程可动手」与「学术可发表」。

### 4.1 场景一：长期重逢（验证 H2 + H3）

**输入**：合成 persona 在时间加速仿真器（continuity-sim，阶段 2 交付物）下与 Life Instance 互动 7 个模拟日，离开 7 个模拟日，再次回来。**仿真器数据生成方法与效度局限声明见 4.6。**

**系统行为规格**：重逢时召回共同事件（episodic 记忆），不立即进入普通问答；分离期间 `social_need`、`attachment` 相关状态按惰性衰减演化；重逢触发 `gentle_reconnection` 行为意图，且行为由状态驱动而非硬编码脚本；关系更新可回放重算。

**验证输出**：核心事实召回率 ≥ 90%；盲测一致率达 4.4 统一门槛；证据链可重放（L0/L1/L2 全链路）。

### 4.2 场景二：对不同的人反应不同（关系可区分性，支撑 H1）

**输入**：同一个 Life Instance 与两个相互独立的单用户关系实例互动（A 高依恋、B 低依恋）。

**系统行为规格**：分别识别人物、分别保存记忆、分别维护关系；相同输入下因 `attachment` 差异产生不同行为意图；不是加载两个 Prompt——行为意图由 Utility Scoring 在结构化状态上计算。

**验证输出**：称呼与关系一致率 ≥ 95%；行为意图差异可由 `reason` 证据链解释（人审）；记忆隔离：A 的记忆不被 B 的会话召回（依赖 MemoryRecord 的 `subject_id` 谓词强制过滤，见架构文档 §5.2）。

### 4.3 场景三：换模型，它还是它（验证 H1，核心）

**输入**：相同结构化状态下，生成侧模型从 Provider A（云端大模型，锁定版本）热切换到 Provider B（本地开源模型，固定权重）。

**系统行为规格**：Identity / 核心记忆 / 关系状态 / 人格参数不变；Context Assembly 将 `[状态 + Top-K 记忆 + 关系得分 + 人格契约]` 动态注入新模型 System Role；Eval Harness 自动注入 100 条核心事实测试集。

**语言控制（v0.9 新增）**：全部评测材料中文锁定（§9.6）；实验报告附两模型中文通用能力基线（无状态条件下同一批事实问答准确率），用于区分连续性治理效果与模型语言能力差异。

**验证输出**：核心事实召回率 ≥ 90%；人格漂移度 ≤ 0.15（RMSD 定义见 3.2）；跨模型行为意图一致率 ≥ 80%（30 个固定场景探针）；切换前后关系状态 / Identity 字段零变化（硬门）。

### 4.4 四基线对照与盲测统计规范

**基线实现规范（v0.9 新增）**：公平对照要求四臂共用**同一生成模型、同一语言渲染模板骨架与同一 Policy 审批**，差异仅在「身份上下文组装」层：

| 基线 | 配置（统一生成侧后的差异） |
|---|---|
| Baseline A | 人格契约 + 近期对话原文（有界窗口），无状态/记忆/关系层 |
| Baseline B | Baseline A + 对话历史摘要（同一模型生成） |
| Baseline C | Baseline A + 标准向量 RAG（同一 embedding 模型检索会话转写），无状态、无关系 |
| **LifeOS** | 状态 + 记忆 + 关系 + 行为规划全链路 |

盲测材料一律从各臂的**完整输出管线**取样，不允许手工拼接。

**Gate 条件**：LifeOS 盲测一致率 ≥ 75%，且 ≥ 最佳基线 + 10 个百分点，且用户能解释感知差异来源（编码方案见 4.5）。

**统计规范（v0.9 更新口径）**：n ≥ 50 为**总样本下限**；被试内配对设计（见 4.5）；报告各臂一致率 bootstrap 95% 置信区间，配对差值 CI 下限须高于最佳基线点估计；分析计划（门槛、检验方法、剔除规则、**功效核算**）在数据收集前预注册并入 gold set 版本管理；盲测与人审至少 1 名非直接开发成员参与。

**基线扩展选项**（沿用 v0.8，按需评审）：将 Portable Agent Memory 协议（arXiv 2605.11032）作为 Baseline D——「迁移状态但不治理连续性」的对照组，用于分离「状态迁移」与「连续性治理」的贡献。

### 4.5 盲测设计（v0.9 新增）

- **被试与招募**：总样本 n ≥ 50（下限），候补名单 1.5×；剔除标准预注册（项目组成员及其直系亲属排除等）；未成年人不纳入。
- **材料**：每臂输出取自统一场景探针集（30 个固定场景）中的重逢/换模型片段，经各臂完整输出管线生成并统一渲染；材料池与呈现顺序在预注册文档中冻结。
- **程序（被试内配对）**：每名被试对**四个臂**在同一场景上的输出对做「是不是同一个它」二选一判断 + 自由文本理由；臂间呈现顺序用拉丁方平衡。判断单位 = 被试 × 臂 × 场景；每臂获得 n ≥ 50 份判断（被试内设计优于每臂 12～13 人的被试间设计——本口径取代讨论稿中「每臂约 12～13 人」的表述，见附录 A-B3）。
- **分析**：各臂一致率（bootstrap 95% CI）；LifeOS 与最佳基线的**配对差值** bootstrap CI；自由文本理由按预注册编码本（状态/关系/记忆三类归因 + 其他）由两名评分员独立编码，Cohen's κ ≥ 0.6（暂定）视为可接受，分歧仲裁——用于「用户能解释差异来源」验收。
- **功效**：预注册时按预期效应（配对差 +10pp）与组内相关做功效核算，不足则扩样（暂定上限 n ≤ 100，走 ADR）。

### 4.6 continuity-sim 数据生成方法与效度局限（v0.9 新增）

- **分层生成**：确定性事件骨架（脚本化日历/作息/事件类型序列，全种子化可复现）+ LLM 对话填充（合成 persona 驱动）+ 可控注入算子（分离/重逢/纠正/冲突/偏好变化按设定概率插入）。
- **效度局限声明（诚实边界）**：LLM 合成对话存在风格单一与分布偏差，H2 的结论限定为「在该合成分布下」成立；阶段 3 真人 dogfood 数据作为外部效度的补充验证，两者结论不互相替代。

## 5. 系统架构（概述）

详细设计见《LifeOS 架构设计 v0.9》。本章只保留验收所需的架构级承诺：

1. **确定性主干 + 概率性叶子**：Life Kernel / Relationship Engine / Behavior Planner / Policy Engine 全部为确定性代码；LLM 仅做候选意图生成、记忆抽取、语言渲染。
2. **三级事件模型**：L0 原始事件 → L1 LLM 解释事件（存档完整模型 provenance）→ L2 权威领域事件。**只有 L2 能修改权威长期状态**；回放时用存档的 L1 重算 L2，无需重新调用 LLM，重放一致率须为 100%。
3. **单一权威数据源**：PostgreSQL 16 + pgvector。
4. **对载体的边界**：LifeOS 对外只暴露「事件注入 API」与「行为意图 + 语言输出 API」，不输出任何运动控制指令；载体如何表达行为意图由下游决定。
5. **部署形态（v0.9 新增）**：单机 Docker Compose，多 Life Instance 共库共存，每实例串行事件队列；跨实例隔离（全部读写强制 `life_id` 谓词）为架构验收项。

## 6. 核心模块 v0 规格（概述）

字段级设计见《LifeOS 架构设计 v0.9》。

- **Life Kernel v0**：5 状态 + valence/arousal 二维情绪（**valence/arousal 来自 L1 抽取的结构化情绪字段，经确定性规则聚合，不由 LLM 直写权威状态**）；人格参数种子生成并冻结于 Identity；惰性衰减 `x(t)=b+(x(t0)-b)e^{-λ(t-t0)}`，仅在读取/事件/快照/评估/导出时物化。明确不做：状态空间模型、HMM、个体参数学习、在线学习。
- **Memory OS v0**：三类记忆；写入管线 `Raw Event → L1 抽取 → Schema 校验 → 重复检测 → 槽位冲突规则 → Policy 校验 → L2 Commit → PostgreSQL`，Embedding 生成走异步 Outbox（记录 `embedding_model_version`）；召回管线 `Context → life_id/subject_id/时间/类型 SQL 过滤 → pgvector 检索 → Reranking → Context Assembly`，先精确检索，性能证明需要才上 ANN；同槽位冲突采用**确定性时态规则**（保留 valid_time / transaction_time 双时间，supersedes/ambiguous 状态机），LLM 只提议不裁决。
- **Relationship Engine v0**：三维关系，透明有界规则 `r_{t+1}=clip(r_t + w_e·p·c − λΔt, 0, 1)`，变化可回放重算。
- **Behavior Planner v0**：6～12 行为用 Utility Scoring；输出含 `reason` 证据链的结构化行为计划，**带 `status` 生命周期（proposed/approved/rejected/executed）**；行为 >15、需多层 fallback、需中断恢复时再引入 py_trees。
- **Policy Engine v0**：自研轻量规则引擎，策略即代码，10 条红线自动化用例，`PolicyDecision` 实体留痕。
- **Model Gateway**：自研轻量 Adapter，双 Provider **实例级绑定**热切换，分层路由，逐笔成本记录。
- **Life Studio v0（调试台）**：基于 Gradio/Streamlit，仅状态可视化、记忆回放、评估面板；**不是产品交互界面**。
- **Eval Harness v0**：八项指标计算、gold set 经 GoldSetRegistry 版本化、CI 集成、盲测问卷工具、回放取证接口。

## 9. 数据治理与合规（v0.9 重构为编号子节）

「长期连续性」只能靠长周期数据验证；真人数据一旦引入（阶段 3），合规就是前置条件。**阶段 0～2 仅使用合成数据，不涉及真人个人信息，PIPL 相关义务自阶段 3 起（9.4）。**

### 9.1 双轨数据获取

- **continuity-sim 时间加速仿真**（目标 1 真实日 ≈ 30 模拟日，阶段 2 交付物）：数据生成方法与效度局限见 4.6；
- **真人 dogfood cohort**（阶段 3：Pilot 10～15 人 2 周 → 正式 30～50 人 4～8 周）：启动前置条件见 9.4 与《研发路线图 v0.9》阶段 3。

### 9.2 Gold Set

- 记忆抽取 gold set ≥ 300 条双人标注 + 仲裁；核心事实集阶段 0 交 50 条、阶段 1 扩至 100 条；人格探针集 40 题中文情境化问卷（预测试要求见 3.2）；30 个行为场景探针；
- 全部**中文编写**（9.6）、全部注册于 GoldSetRegistry 版本化入库冻结（架构 §4）。

### 9.3 隐私分级与删除可验证

- `privacy_level` 四级；sensitive 不进训练/评估/主动话题；评估与生产数据物理隔离；
- **两级删除语义（v0.9 明确）**：
  - **治理性失效**：bitemporal supersedes/expire，历史版本保留（冲突治理的正常路径，不删除历史）；
  - **用户擦除**：用户行使删除权（红线第 10 条）触发**物理删除**——权威记录、向量索引、全文索引、缓存全介质清除，删除后自动重建索引并验证不可恢复（一票否决第 5 条）；擦除动作的 L2 事件**只含 memory_id 与操作元数据，不含内容**；
  - **诚实披露**：append-only 事件表（L0/L1）中可能含已删记忆的内容片段，按**30 天滚动备份窗口（暂定，ADR）**自然消亡，备份加密管理；该删除语义在知情同意书中明示（9.4）。

### 9.4 真人参与合规（PIPL 口径，v0.9 落地管辖区）

- **告知—同意**：处理目的、方式、个人信息种类、保存期限充分告知；敏感个人信息（情绪与依恋人审记录等）取得**单独同意**；
- **最小必要与目的限定**：仅收集验证 H2/H3 所需数据；
- **个人权利响应**：查阅/更正/删除/导出通道即红线第 10 条的工程落地（9.3 两级删除语义）；
- **受托处理**：云端模型供应商（Provider A）以受托处理者身份签署数据处理协议；
- **数据出境**：若 Provider A 为境外服务，阶段 3 启动前完成出境合规路径评估（安全评估/标准合同备案/认证，按届时适用口径），否则将 Provider A 替换为境内合规服务，或阶段 3 期间真人数据仅流经本地模型（实验口径变化记录入 ADR）；
- **未成年人**：不纳入 cohort；
- **伦理审查**：阶段 2 末向机构/第三方伦理委员会提交申请，**批准为阶段 3 前置条件**；
- **声明**：本节为工程口径，不构成法律意见，正式合规方案须法务确认。

### 9.5 模型版本冻结政策

- 连续性实验期间锁定模型版本；纵向对比优先本地固定权重模型；gold set 报告须标注模型及版本，否则不可复现；
- **冻结范围包括生成模型与 Embedding 模型（v0.9 扩展）**：Embedding 模型变更会使全部向量索引不可比，变更须全量重嵌入并重跑冻结测试集，版本记入 EmbeddingOutbox 与评估报告（架构 §4、§5.2）。

### 9.6 语言与数据口径（v0.9 新增）

- 评测材料（核心事实集、人格探针、行为场景、记忆抽取 gold set）全部**中文编写**并版本冻结；
- 连续性实验锁定中文；
- 跨模型对比报告必须附两模型中文通用能力基线（无状态条件下同一批事实问答准确率），以区分「连续性治理效果」与「模型语言能力差异」（§2、§4.3）。

## 12. 未达标工程化改进路线（v0.9 内联排查表，文档自包含）

不能一见指标未达标就加模型和基础设施。先按下表定位失败层：

| 症状 | 首查层 | 排查动作 |
|---|---|---|
| 召回失败 | 记忆写入/过滤/检索 | L1 抽取覆盖 → SQL 谓词（life_id/subject_id/时间/类型）→ 检索排序 |
| 核心事实错误 | L1 抽取 | 抽取 prompt 与 Schema 校验 → gold set 回归 |
| 记忆冲突混乱 | 槽位时间模型 | slot_key 归一 → 双时态字段 → 裁决规则 |
| 换模型像换人 | Context Assembly | 注入完整性 → 模板版本 → Top-K |
| 行为不自然 | Utility 与状态模型 | 权重表 → 衰减参数 → 冷却时间 |
| 两模型行为不同 | LLM 控制下沉 | 是否把本应确定性的决策留给了 LLM |
| 用户无感连续性 | 行为与关系表达 | 重逢意图触发 → 关系差异表达 |
| 成本过高 | 路由分级 | Tier 比例 → 降档实验 |
| P95 过高 | SQL 与候选集 | 索引 → 精确检索 → ANN 引入评审 |
| Policy 漏拦 | 策略覆盖 | 红线用例差分 → 新增规则 |

每轮整改控制在 2～4 周，只解决一个明确假设，重跑同一冻结测试集。连续两轮无改善，应改变设计假设而非无限投入。

## 14. 开源策略与商业边界

- **项目自身许可证**：运行时内核与 Schema / SDK / 评估基准 Apache-2.0（数据 CC BY 4.0）；文档 CC BY 4.0。
- **贡献治理**：DCO 不强制 CLA；CODEOWNERS + 双人评审；Conventional Commits + SemVer；ADR；LifeOS 名称与标识为项目商标，不随分叉授权。
- **开源**：运行时内核、Schema、事件协议、评估基准；**商业**（决策门后另行立项）：载体产品、托管服务、企业支持、专有数据集。
- **原则**：核心能力永不收回闭源，不做 open core 诱饵；竞争力来源是自有生命数据模型、关系动力学、记忆治理、行为协议与评价体系。

## 15. 项目决策原则

- 第一阶段冻结的不是完整产品，而是 Life Instance Schema、L0/L1/L2 事件协议、核心事实集、30 个行为场景、Gate 1 七项硬指标。
- 领域接口第一天冻结，基础设施按需引入。
- 创新集中在 I1～I6，不声称在基础模型/数据库/推理引擎/事件溯源/时态数据库理论上有创新。
- 任何「目前无人做过」的新颖性声明，必须先经查证再写入文档（v0.8 §8 即按此原则重写；v0.9 沿用基线，季度重跑检索式）。
- **LifeOS 是主要矛盾，交互与载体是次要矛盾**：范围边界（1.1）的变更须走 ADR 并经决策层批准。
- **边界参数（1.2）与统计口径（3.2/4.4/4.5）的变更同样走 ADR**（v0.9 新增）。

## 16. 结论

LifeOS 的竞争力不来自使用了多少数据库或 Agent Framework，而来自是否能证明：同一个生命实例经过长期互动、模型升级和载体迁移之后，仍能以稳定、可信、可解释的方式保持「它还是它」。本规格把这一承诺拆解为：

- **3 条可证伪假设**（H1/H2/H3）；
- **8 项量化指标（每项均给出可操作定义）+ 6 项一票否决硬门**；
- **3 个典型场景 + 4～5 基线对照 + 预注册统计规范与盲测设计**；
- **全开源技术栈 + 6 个经文献验证收窄后的真实创新点**（文献基线 2026-08-05，季度复核）；
- **4 阶段逐级授权交付**（1～2 → 6～10 → 12～20 → 24～40 人月）。

决策门前只证明「它还是它」。决策门后，再谈扩张。
