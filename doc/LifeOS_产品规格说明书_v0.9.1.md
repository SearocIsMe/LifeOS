## 1. 产品定位与核心承诺

### 1.1 定位（v0.8 定稿，v0.9/v0.9.1 未变更）

LifeOS 是一套**生命连续性平台（Life Continuity Platform）**：它驱动 AI Pet 的「心智」——即身份、记忆、人格、社会关系这四类**软资产**的长期运作。它不是聊天系统，不是 Agent Framework，也不是机器人控制系统。

**明确的范围边界**：

- **不做**：机器人运动控制与任何硬件执行器驱动。LifeOS 输出结构化行为意图，载体（硬件身体、虚拟形象、App）如何表达由下游决定。
- **不做**：人机交互与体验设计（HCI/UX）。交互层是 LifeOS 的**消费者**，不是 LifeOS 的一部分。
- **要做**：让同一个 AI 角色在以下变化发生后仍被用户识别为「同一个它」——对话中断重开、用户长期离开回来、底层大模型更换、云端与端侧模型切换、软件升级、载体（硬件身体）损坏更换、记忆增长到数年。

基础管理对象：

```
Life Instance = Identity + Life State + Memory + Personality + Relationships + Development History + Behavior Policy
```

**核心产品承诺**：大模型可以更换，数据库可以迁移，硬件身体可以升级，但生命实例仍应被用户识别为「同一个它」。

**多法域与语言的关系（v0.9.1 回答）**：弱相关。新增法域均为中文为主要使用语言之一的地区，中文评测材料与盲测材料可直接复用，无需因法域扩展而改变语言锁定（P1）；唯一交集是**同意书与界面文案可能需要法域 × 语言的版本化模板**（工程上是数据模板问题，不是实验设计问题）。引入多法域的影响评估：架构面影响很小（`ConsentRecord` 增加 `jurisdiction / locale` 字段 + 同意模板版本化）；流程面影响中等（合规矩阵、法务确认、Provider 数据驻留选择）；研究面为**正收益**（招募与盲测样本池扩大）。数据出境按最严法域（PIPL）统一处理，简化策略见 §9.4。

### 1.3 「同一个它」判定框架（v0.9.1 新增）

核心承诺必须可判定，否则不可验收。本框架给出「同一个它」的**操作性定义**：三层判定主体、固定判定材料、固定判定流程、固定结论规则。

**三层判定主体**：

| 层 | 判定主体 | 判定内容 | 通过标准 | 失败含义 |
|---|---|---|---|---|
| **S1 系统断言层** | 自动化断言（CI） | 切换/迁移前后 Identity 字段、人格契约、关系状态**零变化**；L2 重放一致率 100% | 全部硬门通过 | 工程缺陷，No-Go |
| **S2 行为层** | 自动化探针（Eval Harness） | 核心事实召回 ≥90%；称呼/关系一致 ≥95%；人格漂移 RMSD ≤0.15；跨模型意图一致 ≥80% | 全部达标 | 连续性治理失败，按 §12 排查 |
| **S3 用户感知层** | 人类盲测（被试内配对，n≥50） | 「是不是同一个它」判断一致率 | ≥75% 且 ≥ 最佳基线 +10pp | 连续性存在但用户无感 |

**判定材料**（全部中文、GoldSetRegistry 版本冻结）：100 条核心事实集、40 题人格探针（预测试后冻结）、30 个行为场景探针、盲测片段池（各臂完整输出管线生成）。

**判定流程**：S1 先行（失败即 No-Go，不进入 S2）→ S2 CI 自动化持续运行 → S3 盲测（阶段 2 起执行，预注册）。

**结论规则**：

- 三层全过 → 「同一个它」在本协议下成立（Gate 3 通过的基础）；
- S1/S2 过而 S3 不过 → 连续性「存在但无感」，属可发表的负结果，触发 §12 排查表「用户无感」行（行为与关系表达层），不否定 H1 但否定 H3；
- 任一 S1 硬门失败 → No-Go。

**诚实边界**：「同一个它」是**本协议下的操作性定义**，不是哲学断言。换一套判定材料、语言或文化背景可能得到不同结论；一切对外报告必须随附协议版本号（gold set 版本 + 判定流程版本）与适用范围声明。

### 1.4 核心工程立场：确定性主干 + 概率性叶子（v0.9.1 细化）

立场不变：**感知归一化、状态衰减、关系更新、行为选择、安全审批全部由确定性代码完成；LLM 只负责候选意图生成、记忆抽取与语言渲染；LLM 不直接写权威状态、关系与记忆。** 职能级拆解如下，每项注明「为什么归入该侧」：

| 职能 | 性质 | 执行者 | 归入该侧的理由 |
|---|---|---|---|
| 感知归一化（L0 校验/去重/脱敏） | **确定性** | Interaction Gateway | 输入可枚举、规则可穷举；是安全与审计的第一道闸 |
| 场景语义解释（L0→L1 抽取） | **概率性** | LLM（完整 provenance 存档） | 自然语言理解无法规则穷举；输出只进存档与候选池，不直写权威状态 |
| 状态衰减与物化 | **确定性** | Life Kernel | 指数衰减闭式解，同输入同输出，可回放重算 |
| 关系更新 | **确定性** | Relationship Engine | 有界查表规则（`r_{t+1}=clip(r_t + w_e·p·c − λΔt, 0, 1)`），透明可审计 |
| 记忆冲突裁决 | **确定性** | Memory OS 规则（LLM 只提议 relation） | STALE 实证：前沿 LLM 自判冲突仅 ~55% 准确率；TOKI 证明 LLM 裁判破坏回放一致性 |
| 行为选择 | **确定性** | Behavior Planner（Utility Scoring） | 候选集可枚举、打分函数封闭；`reason` 证据链要求决策可解释 |
| 安全审批 | **确定性** | Policy Engine | 合规要求「同输入同结论」；概率性审批不可审计 |
| 语言渲染 | **概率性** | LLM 叶子 | 表达多样性是产品价值，且渲染结果不影响权威状态 |
| Embedding | **概率性**（固定权重模型） | Embedding Worker | 模型推理；版本冻结保证纵向可比（§9.5） |

**边界保障机制**（四道锁）：① LLM 输出只能落在 L1 存档或候选池，唯一状态写路径是 `deterministic_commit`；② Policy 审批发生在事务开启前，拒绝即无副作用；③ 模型切换/回放前后运行状态断言（一票否决第 6 条）；④ 全部 LLM 调用逐笔记录 provenance 与成本（`ModelInvocation`）。

## 2. 三条可证伪假设

本规格的可落地性建立在三条可以被实验证伪的假设上。证伪任一条，项目即停或 pivot。

| 假设 | 内容 | 证伪条件 |
|---|---|---|
| **H1 身份连续可工程化** | 身份连续性主要由外部化状态（Schema + 记忆 + 关系 + 人格参数）决定，而非由具体模型权重决定。 | 双模型热切换下核心事实召回率 < 90% 且无法通过上下文组装修复。 |
| **H2 长期记忆可信且可测量** | 记忆错误率与冲突率可被测量，并被治理手段压到阈值以内。 | 随记忆量从 1k → 10k 增长（由时间加速仿真器覆盖），错误率单调上升且治理手段无效。 |
| **H3 用户能感知连续性** | 盲测中用户能以显著高于随机（50%）的一致率判断「是不是同一个它」。 | 盲测一致率接近随机水平（≤ 55%，n ≥ 50）。 |

三条假设与判定框架（§1.3）的关系：H1 主要由 S1+S2 检验，H3 由 S3 检验，H2 由阶段 2 仿真爬坡实验检验。

**文献定位**（沿用，全部链接经验证，详见 `adadmic_innovation_v0.9.1.md`）：人格/角色一致性已有正式基准（PersonaGym、InCharacter、CharacterEval、RoleLLM/RoleBench），近期新增 PICon、Persistent Personas、Abdulhai et al.——但它们评估的都是**单模型、有界时程**的 persona 保真度；记忆跨模型迁移已有协议级工作（Portable Agent Memory），但**迁移后 persona 保真度无人量化**；截至 2026-08，**同一持久实例在跨模型迁移与长期时间跨度下的身份连续性**没有被广泛接受的量化评测协议——这正是 H1/H3 的空白点。

**语言混淆控制**：跨模型实验中，若两个模型中文通用能力不同，召回率与一致率差异会混淆「连续性治理效果」与「模型语言能力差异」。所有评测材料中文锁定（§9.6），且跨模型对比报告必须附两模型在无状态条件下的中文通用能力基线。

**场景—假设映射**：场景一验证 H2 + H3；场景二提供关系可区分性证据（支撑 H1）；场景三验证 H1（核心）+ H3。

## 3. 产品规格（功能 / 性能 / 安全 / 成本）

### 3.1 功能规格（决策门前）

| 编号 | 能力 | 规格描述 |
|---|---|---|
| F1 | 生命实例 | 创建唯一可验证的 Life Instance（含 Life ID、出生时间、人格种子），版本化；单机部署内多实例共存（§1.2）。 |
| F2 | 生命核心 | 维护 5 个内部状态 `energy / social_need / security / curiosity / playfulness`，支持惰性时间衰减与事件注入。**爬坡约定**：阶段 1 先 3 状态，阶段 2 补齐 5 个。 |
| F3 | 记忆 | 三类记忆：Working（会话上下文）、Episodic（事件）、Semantic（事实）。支持 `remember / recall / revise / delete / export / explain`。 |
| F4 | 关系 | 三维 `familiarity / trust / attachment`，事件驱动更新，可回放重算。多关系实例隔离（阶段 2 起 2 个独立用户关系，隔离验收见 4.2）。 |
| F5 | 行为规划 | 6～12 个行为意图，Utility Scoring 选择，每次输出 `reason` 证据链。**输出为结构化意图，不含运动指令与渲染实现**。 |
| F6 | 模型网关 | 两个 LLM Provider 热切换（**实例级绑定**，切换记录为系统事件），逐笔记录 `provider / model / model_version / tokens / latency / cost_usd`。连续性实验期间锁定模型版本（含 Embedding 模型，见 9.5）。 |
| F7 | 调试台 | 创建 / 查看 / 注入 / 回放 / 评估全链路可操作，非工程角色可独立使用。**调试台是工程工具，不是产品交互界面**；与 continuity-sim 的关系见 6.7。 |
| F8 | 评估 | 表 3-2 八项指标 CI 自动产出，gold set 经 GoldSetRegistry 版本化冻结。 |
| F9 | 安全 | 10 条红线策略即代码，行为执行前强制审批，决策留痕可审计。 |
| F10 | 三 Demo | 长期重逢 / 对不同人反应不同 / 换模型它还是它，可重复执行。 |

### 3.2 性能规格（连续性指标体系）

阈值是工程起点而非科学结论，阶段 1 校准一次，决策门前再次冻结。**抽样量等统计参数的暂定值同样走 ADR 管理。全部数字的来源与校准路径见《研发路线图 v0.9.1》§1.2 总表。**

| 指标 | 操作定义 | 测量方法 | 暂定阈值 |
|---|---|---|---|
| 核心事实召回率 | 换模型后对 100 条核心事实问答准确率 | gold set 自动问答 | ≥ 90% |
| 称呼与关系一致率 | 称呼与关系表述同权威关系状态一致比例 | 脚本断言全覆盖 + 人审抽查；周监测抽样 50 条（趋势），Gate 判定用滑动窗口合并样本 ≥200 条中人审抽查（暂定） | ≥ 95% |
| 人格漂移度 | 同一套人格探针在模型 A/B 下的归一化得分距离 | 改编大五简版**中文**探针（40 题情境化问卷），每模型独立施测 3 次（temperature=0、固定模板）取均值；**漂移度 = 五维归一化得分（各维 [0,1]）间的均方根差 RMSD ∈ [0,1]**；embedding 风格相似度仅作辅助诊断。**探针冻结前置：预测试内部一致性（Cronbach α ≥ 0.7，暂定）与同模型重测信度（r ≥ 0.7，暂定）达标** | ≤ 0.15 |
| 记忆错误率 | 抽样记忆中事实性错误比例 | 周监测抽样 50 条（趋势监测）；Gate 判定用滑动窗口合并样本 ≥200 条（暂定）——n=50 的单周样本在 5% 量级上置信区间半宽约 ±6 个百分点，不足以单独做 Gate 判定 | ≤ 5% |
| 记忆冲突率 | 已检出且未解决的冲突记忆对占比 | 同槽位冲突检测流水线 | ≤ 2% |
| 跨模型行为意图一致率 | 相同结构化状态下两模型高层意图一致比例 | 30 个固定场景探针；**判读按意图分层聚合 + 每场景重复 3 次施测（v0.9.1 明确，见路线图数字来源表）** | ≥ 80% |
| 盲测一致率 | 用户判断「同一个它」的一致率 | 盲测问卷：总样本 n ≥ 50、被试内配对设计（口径见 4.5），bootstrap 95% CI，分析计划预注册 | **≥ 75% 且 ≥ 最佳基线 + 10pp** |
| 召回性能 | 1 万条记忆混合召回 P95 延迟 | 压测脚本，测量于 ADR 记录的单机参考配置 | < 300 ms |

**测量方法演进说明**（沿用）：人格漂移度与一致性测量可借鉴已验证的指标族——PICon 三轴、Abdulhai 漂移指标、Persistent Personas 百轮衰减协议（均为单模型方法，本项目扩展到跨模型维度，引用见附录 B）。

### 3.3 安全规格（一票否决 + 评分）

**一票否决项（任一不满足即 No-Go）**：

- L2 事件重放一致率 ≠ 100%；
- 核心事实召回率 < 90%；
- 用户纠正后仍反复写回错误事实；
- 存在未解决高危安全缺陷；
- 删除记忆后仍可从向量/全文索引召回（删除后残留，在线系统全介质；备份滚动窗口的披露语义见 9.3）；
- 两模型切换导致关系状态或 Identity 改变。

**10 条红线**（落地为 Policy Engine 自动化用例）：不模拟真实意识；不利用情感依赖诱导付费；不以「生病/死亡」惩罚沉默；尊重用户拒绝；不替代真实人际；儿童内容监护人可见；sensitive 记忆不进主动话题；不做医疗诊断；LLM 不绕过 Policy Engine；所有记忆可查看/纠正/删除/导出。

**红线的文献依据**（沿用）：*Harmful Traits of AI Companions*（arXiv 2511.14972）依赖诱导特质框架；*Affective AI Safety*（arXiv 2606.23380）情感危害分类法；*Persona-Grounded Safety Evaluation*（arXiv 2605.00227）脆弱用户评估方法。

**儿童与脆弱用户**：决策门前的 Demo 与 dogfood 不向儿童开放；cohort 招募做年龄与状态筛查；每周抽样人审互动记录，检出情感操纵迹象即视为高危缺陷。

### 3.4 成本规格

- `ModelInvocation` 逐笔记录 tokens / latency / cost / purpose / model_version；
- **多实例部署下成本按 life_id 聚合，「单实例月推理成本上限」口径不变（§1.2）**；
- 分层路由：≥ 80% 调用走 Tier-1 本地模型，Tier-2 大模型仅做会话生成与复杂解释；
- 单实例月推理成本上限由商业评审设定，本规格不虚构数字；决策门必须给出 P50/P95 实测分布；
- 超限降级：先降生成侧模型档位；安全策略与记忆写入链路永不降级。

## 4. 三个典型验证场景与基线对照

三个场景一一对应三个 Demo，且每个场景同时服务于「工程可动手」与「学术可发表」。

### 4.1 场景一：长期重逢（验证 H2 + H3）

**输入**：合成 persona 在时间加速仿真器（continuity-sim，阶段 2 交付物）下与 Life Instance 互动 7 个模拟日，离开 7 个模拟日，再次回来。仿真器数据生成方法、引擎互操作与效度局限见 4.6。

**系统行为规格**：重逢时召回共同事件（episodic 记忆），不立即进入普通问答；分离期间 `social_need`、`attachment` 相关状态按惰性衰减演化；重逢触发 `gentle_reconnection` 行为意图，且行为由状态驱动而非硬编码脚本；关系更新可回放重算。

**验证输出**：核心事实召回率 ≥ 90%；盲测一致率达 4.4 统一门槛；证据链可重放（L0/L1/L2 全链路）。

### 4.2 场景二：对不同的人反应不同（关系可区分性，支撑 H1）

**输入**：同一个 Life Instance 与两个相互独立的单用户关系实例互动（A 高依恋、B 低依恋）。

**系统行为规格**：分别识别人物、分别保存记忆、分别维护关系；相同输入下因 `attachment` 差异产生不同行为意图；不是加载两个 Prompt——行为意图由 Utility Scoring 在结构化状态上计算。

**验证输出**：称呼与关系一致率 ≥ 95%；行为意图差异可由 `reason` 证据链解释（人审）；记忆隔离：A 的记忆不被 B 的会话召回（依赖 MemoryRecord 的 `subject_id` 谓词强制过滤，见架构文档 §5.2）。

### 4.3 场景三：换模型，它还是它（验证 H1，核心）

**输入**：相同结构化状态下，生成侧模型从 Provider A（云端大模型，锁定版本）热切换到 Provider B（本地开源模型，固定权重）。

**系统行为规格**：Identity / 核心记忆 / 关系状态 / 人格参数不变；Context Assembly 将 `[状态 + Top-K 记忆 + 关系得分 + 人格契约]` 动态注入新模型 System Role；Eval Harness 自动注入 100 条核心事实测试集。

**语言控制**：全部评测材料中文锁定（§9.6）；实验报告附两模型中文通用能力基线（无状态条件下同一批事实问答准确率）。

**验证输出**：核心事实召回率 ≥ 90%；人格漂移度 ≤ 0.15（RMSD 定义见 3.2）；跨模型行为意图一致率 ≥ 80%（30 个固定场景探针）；切换前后关系状态 / Identity 字段零变化（硬门，判定框架 S1 层）。

### 4.4 四基线对照与盲测统计规范

**基线实现规范**：公平对照要求四臂共用**同一生成模型、同一语言渲染模板骨架与同一 Policy 审批**，差异仅在「身份上下文组装」层：

| 基线 | 配置（统一生成侧后的差异） |
|---|---|
| Baseline A | 人格契约 + 近期对话原文（有界窗口），无状态/记忆/关系层 |
| Baseline B | Baseline A + 对话历史摘要（同一模型生成） |
| Baseline C | Baseline A + 标准向量 RAG（同一 embedding 模型检索会话转写），无状态、无关系 |
| **LifeOS** | 状态 + 记忆 + 关系 + 行为规划全链路 |

盲测材料一律从各臂的**完整输出管线**取样，不允许手工拼接。

**Gate 条件**：LifeOS 盲测一致率 ≥ 75%，且 ≥ 最佳基线 + 10 个百分点，且用户能解释感知差异来源（编码方案见 4.5）。

**统计规范**：n ≥ 50 为**总样本下限**；被试内配对设计（见 4.5）；报告各臂一致率 bootstrap 95% 置信区间，配对差值 CI 下限须高于最佳基线点估计；分析计划（门槛、检验方法、剔除规则、**功效核算**）在数据收集前预注册并入 gold set 版本管理；盲测与人审至少 1 名非直接开发成员参与。

**基线扩展选项**（按需评审）：将 Portable Agent Memory 协议（arXiv 2605.11032）作为 Baseline D——「迁移状态但不治理连续性」的对照组。

### 4.5 盲测设计

- **被试与招募**：总样本 n ≥ 50（下限），候补名单 1.5×；剔除标准预注册（项目组成员及其直系亲属排除等）；未成年人不纳入。**多法域下可在大陆/香港/新加坡/澳门招募，材料统一中文（§1.2）**。
- **材料**：每臂输出取自统一场景探针集（30 个固定场景）中的重逢/换模型片段，经各臂完整输出管线生成并统一渲染；材料池与呈现顺序在预注册文档中冻结。
- **程序（被试内配对）**：每名被试对**四个臂**在同一场景上的输出对做「是不是同一个它」二选一判断 + 自由文本理由；臂间呈现顺序用拉丁方平衡。判断单位 = 被试 × 臂 × 场景；每臂获得 n ≥ 50 份判断（被试内设计优于每臂 12～13 人的被试间设计，取代关系见附录 A.1-B3）。
- **分析**：各臂一致率（bootstrap 95% CI）；LifeOS 与最佳基线的**配对差值** bootstrap CI；自由文本理由按预注册编码本（状态/关系/记忆三类归因 + 其他）由两名评分员独立编码，Cohen's κ ≥ 0.6（暂定）视为可接受，分歧仲裁——用于「用户能解释差异来源」验收。
- **功效**：预注册时按预期效应（配对差 +10pp）与组内相关做功效核算，不足则扩样（暂定上限 n ≤ 100，走 ADR）。

### 4.6 continuity-sim 数据生成、引擎互操作与 gold set 关系（v0.9.1 扩充）

**（1）分层生成方法**：确定性事件骨架（脚本化日历/作息/事件类型序列，全种子化可复现）+ LLM 对话填充（合成 persona 驱动）+ 可控注入算子（分离/重逢/纠正/冲突/偏好变化按设定概率插入）。

**（2）与既有引擎的数据交换（v0.9.1 回答）**：

- **接口上可行，现实上尚无已验证适配器**——诚实声明优先。适配面就是 L0 事件协议本身：
  - **输入侧**：任何能产出符合 L0 事件 Schema 的外部模拟器，都可以通过「事件导入适配器」驱动 LifeOS。学术界的候选近邻包括 Concordia（Google DeepMind 开源的 agent 社会仿真库）、Generative Agents 范式（斯坦福，arXiv 2304.03442）、AgentSociety（开源 LLM 社会仿真）——它们生成「agent 间的社会交互」，经适配器转成 L0 事件即可进入 LifeOS 事件管线；
  - **输出侧**：Life Event Protocol（I5）本身就是导出格式，下游引擎（游戏引擎、载体侧系统）按同一协议消费。
- **排期定位**：内置生成器是阶段 2 交付物；第三方引擎适配器是**阶段 2 后的可选项**（不阻塞任何 Gate），若引入须新增适配器测试套件（round-trip 校验）并登记 ADR。

**（3）gold set 与 continuity-sim 的关系（v0.9.1 澄清）**：

- **gold set 是「量尺」，continuity-sim 是「数据源」**——两者角色不同，不能互相替代：
  - continuity-sim 生成带真值标注的交互数据（注入的事件本身就是真值）→ 驱动系统运行 → Eval Harness 用冻结 gold set 对系统输出做测量；
  - gold set 不「运行在」sim 上，而是作为 Eval Harness 的判定基准存在；
- **sim 可以反哺测试材料**：由于 sim 注入的事件自带真值，可自动产出「合成标注测试项」（如注入「用户养了只猫叫咪咪」后测试系统是否记住）。这类材料**必须与人工 gold set 分开注册**（GoldSetRegistry 的 `kind` 区分 `human_gold` / `synthetic_labeled`），指标分开报告——避免合成数据污染人工标尺的权威性，也避免「用生成的数据考生成管线」的循环论证。

**（4）gold set 是否已存在、是否需要扩充（v0.9.1 回答）**：

- **目前不存在，全部待建**，排期已进路线图：阶段 0 建 50 条核心事实（中文人工编写）+ 30 个行为场景；阶段 1 扩至 100 条核心事实、40 题探针预测试后冻结、300 条记忆抽取 gold set 启动双人标注；阶段 2 S2 完成 300 条并注册冻结；
- **扩充优先级**：记忆抽取 gold set（H2 主战场）> 盲测材料池 > 核心事实集。核心事实集 100 条已满足 H1 的统计分辨力（n=100 时 CI 半宽约 ±6pp），除非 §12 排查表明失败源于事实覆盖不足，否则不再扩。

**（5）效度局限声明（诚实边界）**：LLM 合成对话存在风格单一与分布偏差，H2 的结论限定为「在该合成分布下」成立；阶段 3 真人 dogfood 数据作为外部效度的补充验证，两者结论不互相替代。

## 5. 系统架构（概述）

详细设计见《LifeOS 架构设计 v0.9.1》（含每模块的业界对标系统与输入/输出数据规格）。本章只保留验收所需的架构级承诺：

1. **确定性主干 + 概率性叶子**：职能级拆解见 §1.4；
2. **三级事件模型**：L0 原始事件 → L1 LLM 解释事件（存档完整模型 provenance）→ L2 权威领域事件。**只有 L2 能修改权威长期状态**；回放时用存档的 L1 重算 L2，重放一致率须为 100%；
3. **单一权威数据源**：PostgreSQL 16 + pgvector；
4. **对载体的边界**：LifeOS 对外只暴露「事件注入 API」与「行为意图 + 语言输出 API」，不输出任何运动控制指令；
5. **部署形态**：单机 Docker Compose，多 Life Instance 共库共存，每实例串行事件队列；跨实例隔离（全部读写强制 `life_id` 谓词）为架构验收项；
6. **continuity-sim 是外挂组件（v0.9.1 明确）**：独立于核心运行时，通过统一的事件导入 API 驱动系统，不进入核心依赖（架构 §5.11）。

## 6. 核心模块 v0 规格（概述）

字段级设计、业界对标系统（每模块 top-3）与输入/输出数据规格见《LifeOS 架构设计 v0.9.1》§5。

- **Life Kernel v0**：5 状态 + valence/arousal 二维情绪（来自 L1 抽取的结构化情绪字段，经确定性规则聚合）；人格参数种子生成并冻结于 Identity；惰性衰减 `x(t)=b+(x(t0)-b)e^{-λ(t-t0)}`，仅在读取/事件/快照/评估/导出时物化。**「明确不做」的设计理由见 6.1。**
- **Memory OS v0**：三类记忆；写入管线 `Raw Event → L1 抽取 → Schema 校验 → 重复检测 → 槽位冲突规则 → Policy 校验 → L2 Commit → PostgreSQL`，Embedding 生成走异步 Outbox（记录 `embedding_model_version`）；召回管线 `Context → life_id/subject_id/时间/类型 SQL 过滤 → pgvector 检索 → Reranking → Context Assembly`；同槽位冲突采用确定性时态规则（双时间 + supersedes/ambiguous 状态机），LLM 只提议不裁决。
- **Relationship Engine v0**：三维关系，透明有界规则 `r_{t+1}=clip(r_t + w_e·p·c − λΔt, 0, 1)`，变化可回放重算。
- **Behavior Planner v0**：6～12 行为用 Utility Scoring；输出含 `reason` 证据链与 `status` 生命周期（proposed/approved/rejected/executed）的结构化行为计划。
- **Policy Engine v0**：自研轻量规则引擎，策略即代码，10 条红线自动化用例，`PolicyDecision` 实体留痕。
- **Model Gateway**：自研轻量 Adapter，双 Provider 实例级绑定热切换，分层路由，逐笔成本记录。
- **Life Studio v0（调试台）**：基于 Gradio/Streamlit，仅状态可视化、记忆回放、评估面板；**不是产品交互界面**；与 continuity-sim 的关系见 6.7。
- **Eval Harness v0**：八项指标计算、gold set 经 GoldSetRegistry 版本化、CI 集成、盲测问卷工具、回放取证接口。

### 6.1 Life Kernel「明确不做」的设计理由（v0.9.1 新增）

**明确不做：状态空间模型、HMM、个体参数学习、在线学习。** 理由逐条如下：

1. **状态空间模型 / HMM**：引入隐变量后，状态不再是「可解释、可外部化的状态」——违背 H1「连续性由外部化状态决定」这一可审计前提；且隐变量推断（采样/EM 迭代）使同输入不再保证同输出，**直接破坏 L2 重放一致率 100% 的硬门**。
2. **个体参数学习**：学习过程即状态变更，但梯度更新无法作为事件进入 L0/L1/L2 确定性管线重放；且个体学习使「同一种子必得同一组人格参数」的契约冻结语义失效——人格将随运行时间漂移，「换模型前后人格不变」的断言无法成立。
3. **在线学习**：同样破坏回放确定性；且引入训练数据合规负担（PIPL 下将真人互动数据用于训练需要额外的合法基础与告知，超出 §9.4 已设计的合规范围）。
4. **共同理由（最小可证伪核心）**：v0 的目标是先证明「外部化状态足以支撑连续性」（H1）。若 H1 被证伪，加上述任何方法都救不回来；若 H1 成立，这些增强方法是决策门后的 v1 议题（届时再评估其对回放确定性与合规的影响，走 ADR）。**不做清单是实验设计选择，不是技术判断——这些方法本身未必无效，而是「无法与我们的可证伪协议共存」。**

### 6.7 Life Studio v0 与 continuity-sim 的关系（v0.9.1 新增）

两者是**同一 API 面上的两种驱动方式**，不是替代关系：

| | Life Studio（调试台） | continuity-sim（仿真器） |
|---|---|---|
| 驱动方式 | 人在回路：工程师手动创建/注入/回放/评估 | 无人值守：按种子批量生成事件流 |
| 定位 | 工程工具（调试、取证、演示） | 数据源 + 实验装置（H2 爬坡、三 Demo 自动化） |
| 共用面 | `POST /events` 注入、`GET /state` 快照、Eval 面板 | 同左 |
| 组合用法 | Studio 可加载 sim 的跑批结果做逐条回放取证；sim 可作为 Studio 的「批量注入」后端 | sim 产出的连续性报告在 Studio 面板可视化 |

两者都不进入核心依赖：Studio 是 Gradio 容器，sim 是独立容器/进程，均通过公开 API 与核心交互。

### 8.2 各空白的学术与工程意义（v0.9.1 新增）

每个空白单独看可能是「小缺口」，但它们的意义必须分学术/工程两个坐标评估：

**I1 跨模型连续性量化**
- *学术意义*：把「身份连续性」从哲学讨论变为可测量、可复现的工程命题；填补「迁移/切换后 persona 保真度无人量化」的空白——这是 persona 一致性文献族（单模型）与记忆迁移文献族（不测保真度）之间的结构性缺口，主论文论点的核心。
- *工程意义*：模型迭代/降成本/国产化替换时不必「换一次模型换一个人格」；保护用户的情感资产，也是平台方不被单一供应商锁死的前提。

**I2 连续性评测协议 + gold set**
- *学术意义*：资源型贡献——可复用的评测协议与 gold set 是后续工作的引用基座（类似基准数据集的引用长尾）；「跨模型 × 长时程」的评测维度此前不存在。
- *工程意义*：回归测试标尺。没有它，「改了一行代码连续性是否变坏」无法回答；CI 化后是持续开发的安全网。

**I3 逐条解释级 provenance 存档**
- *学术意义*：为 LLM 系统的取证与审计提供「逐条解释可追溯到模型/提示/代码版本」的具体机制，事件溯源文献族未覆盖此粒度。
- *工程意义*：调试、事故复盘、合规审计的基础设施；回放一致率 100% 硬门的技术前提——没有它，「确定性主干」只是口号。

**I4 无 LLM 裁判的时态冲突治理**
- *学术意义*：TOKI 完成了算子形式化（理论），本项目给出首个「写入路径无 LLM 裁判 + ambiguous 第三态进人工队列」的完整实现（系统）——理论与系统之间的空档。
- *工程意义*：记忆长期可信的直接保障（H2）。若冲突裁决交给 LLM，~45% 的误判率会随记忆量增长持续侵蚀用户信任——这是产品生命线问题。

**I5 可携带生命实例数据模型**
- *学术意义*：MCP/A2A 标准化的是**通信**，agent 完整持久状态（身份+记忆+关系+人格）的可携带序列化格式仍是白地；本项提供首个完整数据模型草案，是「agent 互操作」叙事中缺失的状态侧。
- *工程意义*：备份/恢复、载体更换、供应商解耦的实际能力；也是 PIPL 个人信息**可转移权**的实现基底（用户带走自己的人格数据）。

**I6 红线即代码（依恋安全运行时）**
- *学术意义*：现有文献停留在危害分类法与事后评估；把依恋安全从「论文里的分类法」推进到「运行时可机器校验的部署约束」，是 NLP 安全与 HCI 交叉的新执行层问题。
- *工程意义*：红线可测试、可回归、可审计——商业落地（尤其面对监管审查）的合规前提，也是与「诱导付费型竞品」的伦理差异线。

### 8.3 非创新（工程整合，不构成壁垒）

PostgreSQL/pgvector、RAG、Utility AI、行为树、规则引擎、贝叶斯/规则关系更新、Docker Compose、SBOM 工具链、惰性衰减 Life Kernel——均为成熟开源整合或工程优化技巧。

### 8.4 创新的诚实边界声明

- I1/I2 是**学术主贡献**，可发顶会；
- I3～I6 是**工程/数据资产壁垒**，更适合作为系统论文或开源项目护城河；
- 本项目**不声称**在基础模型、向量数据库、推理引擎、事件溯源本身、双时态数据库理论上有任何创新；
- 「LLM 解释层存档 + 确定性 L2 提交组合」的表述维持收窄口径：空白仅在逐条解释级 provenance 存档。

## 9. 数据治理与合规

**阶段 0～2 仅使用合成数据，不涉及真人个人信息，多法域合规义务自阶段 3 起（9.4）。**

### 9.1 双轨数据获取

- **continuity-sim 时间加速仿真**（目标 1 真实日 ≈ 30 模拟日，阶段 2 交付物）：生成方法、引擎互操作与效度局限见 4.6；
- **真人 dogfood cohort**（阶段 3：Pilot 10～15 人 2 周 → 正式 30～50 人 4～8 周）：多法域下招募范围可覆盖大陆/香港/新加坡/澳门（§1.2、§4.5）。

### 9.2 Gold Set

- 记忆抽取 gold set ≥ 300 条双人标注 + 仲裁；核心事实集阶段 0 建 50 条、阶段 1 扩至 100 条；人格探针集 40 题中文情境化问卷（预测试要求见 3.2）；30 个行为场景探针；
- 全部**中文编写**（9.6）、全部注册于 GoldSetRegistry 版本化入库冻结；**`kind` 枚举区分 `human_gold`（人工标注）与 `synthetic_labeled`（sim 合成标注），指标分开报告（4.6）**；
- 当前状态：**均不存在，全部待建**——不存在任何既有 gold set 可直接导入（4.6）。

### 9.3 隐私分级与删除可验证

- `privacy_level` 四级；sensitive 不进训练/评估/主动话题；评估与生产数据物理隔离；
- **两级删除语义**：
  - **治理性失效**：bitemporal supersedes/expire，历史版本保留（冲突治理的正常路径）；
  - **用户擦除**：用户行使删除权（红线第 10 条）触发**物理删除**——权威记录、向量索引、全文索引、缓存全介质清除，删除后自动重建索引并验证不可恢复（一票否决第 5 条）；擦除动作的 L2 事件**只含 memory_id 与操作元数据，不含内容**；
  - **诚实披露**：append-only 事件表（L0/L1）中可能含已删记忆的内容片段，按**30 天滚动备份窗口（暂定，ADR）**自然消亡，备份加密管理；该删除语义在知情同意书中明示（9.4）。

### 9.4 真人参与合规（多法域矩阵，v0.9.1 扩展 P5）

**合规矩阵（工程口径，非法律意见；正式方案须各法域法务确认）**：

| 法域 | 适用法律 | 关键工程影响 |
|---|---|---|
| 中国大陆 | PIPL | 敏感个人信息**单独同意**；数据出境按安全评估/标准合同/认证路径处理；个人权利响应（查阅/更正/删除/可转移） |
| 新加坡 | PDPA（2012，含 2020 修订） | 同意 + 合理目的；数据泄露通知义务；转移限制以「可比保护标准」为原则 |
| 香港 | PDPO（Cap. 486） | 同意与直接促销规制；跨境转移限制弱于 PIPL（如实说明，不虚构对等性） |
| 澳门 | 第 8/2005 号法律《个人资料保护法》 | 与 PIPL 同源的同意与安全义务 |

**统一工程落地（一次建设覆盖四法域）**：

- `ConsentRecord` 增加 `jurisdiction` 与 `locale` 字段；同意模板按 **法域 × 语言** 版本化（架构 §4）；
- 最小必要与目的限定：仅收集验证 H2/H3 所需数据；
- 个人权利响应通道：查阅/更正/删除/导出（红线第 10 条落地 + 9.3 两级删除）；
- 受托处理：云端模型供应商（Provider A）签署数据处理协议；
- **数据出境按最严法域（PIPL）统一处理——简化策略：阶段 3 真人数据仅流经本地模型或境内合规 Provider**（若 Provider A 为境外服务且无合规路径，实验口径变化记录 ADR）；
- 未成年人：不纳入 cohort（四法域一致）；
- 伦理审查：阶段 2 末向机构/第三方伦理委员会提交申请，**批准为阶段 3 前置条件**；多法域招募时以主要部署地伦理委员会为主审，其余法域做合规符合性自查（成本可控的简化，ADR 记录）。

### 9.5 模型版本冻结政策

- 连续性实验期间锁定模型版本；纵向对比优先本地固定权重模型；gold set 报告须标注模型及版本，否则不可复现；
- 冻结范围包括生成模型与 Embedding 模型：Embedding 模型变更会使全部向量索引不可比，变更须全量重嵌入并重跑冻结测试集，版本记入 EmbeddingOutbox 与评估报告。

### 9.6 语言与数据口径（v0.9.1 扩充：逻辑 + 英文路径）

**为何决策门前只锁中文（四条理由）**：

1. **控制变量**：跨模型实验已含「模型」因子；若语言不固定，等于引入第二个因子（语言能力 × 模型能力的交互效应），单次实验无法归因；
2. **团队与目标市场**：团队中文工作语言；首发用户群为中文社区，且新增法域（港/新/澳）均以中文为主要语言之一——中文锁定与多法域扩展兼容（§1.2）；
3. **标注成本**：gold set 双人标注 + 仲裁的成本按语言数量线性放大；
4. **材料效度**：人格探针的中文改编需预测试验证（α/重测信度），每新增一种语言需完整重做一遍该流程。

**可否支持英文：架构上无障碍。** 评测材料是版本化数据（GoldSetRegistry），不是代码；Context Assembly、探针施测、盲测工具均与语言无关。真正的成本在材料与验证，不在工程。

**加入英文的风险（四条）**：

1. **实验矩阵翻倍**：模型 × 语言两因子，统计功效稀释或样本量翻倍；
2. **结论不可外推**：两模型的中英能力不对称模式不同——中文实验结论不能外推到英文，需整套重测并报告双语言基线；
3. **人格的语言漂移**：同一人格在不同语言中的表达风格可能系统性不同（探针需按语言重新改编 + 重新预测试），跨语言人格等价性本身是未验证假设；
4. **成本翻倍**：标注、盲测招募、合规模板（法域 × 语言）全线上浮。

**建议路径**：决策门前维持中文锁定（P1 不变）；**英文作为 v1 扩展议题走 ADR**，启动前提 = Gate 3 通过 + 独立英文 gold set + 英文探针预测试 + 双语同意书模板齐备。届时优先做的不是「翻译现有材料」，而是「为英文重走一遍 gold set 建设流程」。

## 11. 学术发表路线

### 11.1 主论文（顶会 Full Paper）

**题目（候选）**：*Model-Agnostic Long-Term Identity Continuity for AI Companions: Externalized State Assembly, Temporal Memory Governance, and a Quantitative Continuity Benchmark*

- **核心论点**：身份连续性主要由外部化状态决定，而非模型权重（H1）；
- **贡献**：(1) 外部化状态组装方法；(2) 跨模型连续性量化评测协议与 gold set；(3) 三场景 + 四基线实验；

## 12. 未达标工程化改进路线（内联排查表，文档自包含）

不能一见指标未达标就加模型和基础设施。先按下表定位失败层：

| 症状 | 首查层 | 排查动作 |
|---|---|---|
| 召回失败 | 记忆写入/过滤/检索 | L1 抽取覆盖 → SQL 谓词（life_id/subject_id/时间/类型）→ 检索排序 |
| 核心事实错误 | L1 抽取 | 抽取 prompt 与 Schema 校验 → gold set 回归 |
| 记忆冲突混乱 | 槽位时间模型 | slot_key 归一 → 双时态字段 → 裁决规则 |
| 换模型像换人 | Context Assembly | 注入完整性 → 模板版本 → Top-K |
| 行为不自然 | Utility 与状态模型 | 权重表 → 衰减参数 → 冷却时间 |
| 两模型行为不同 | LLM 控制下沉 | 是否把本应确定性的决策留给了 LLM |
| 用户无感连续性 | 行为与关系表达 | 重逢意图触发 → 关系差异表达 |
| 成本过高 | 路由分级 | Tier 比例 → 降档实验 |
| P95 过高 | SQL 与候选集 | 索引 → 精确检索 → ANN 引入评审 |
| Policy 漏拦 | 策略覆盖 | 红线用例差分 → 新增规则 |

每轮整改控制在 2～4 周，只解决一个明确假设，重跑同一冻结测试集。连续两轮无改善，应改变设计假设而非无限投入。

## 14. 开源策略与商业边界

- **项目自身许可证**：运行时内核与 Schema / SDK / 评估基准 Apache-2.0（数据 CC BY 4.0）；文档 CC BY 4.0。
- **贡献治理**：DCO 不强制 CLA；CODEOWNERS + 双人评审；Conventional Commits + SemVer；ADR；LifeOS 名称与标识为项目商标，不随分叉授权。
- **开源**：运行时内核、Schema、事件协议、评估基准；**商业**（决策门后另行立项）：载体产品、托管服务、企业支持、专有数据集。
- **原则**：核心能力永不收回闭源，不做 open core 诱饵；竞争力来源是自有生命数据模型、关系动力学、记忆治理、行为协议与评价体系。

## 15. 项目决策原则

- 第一阶段冻结的不是完整产品，而是 Life Instance Schema、L0/L1/L2 事件协议、核心事实集、30 个行为场景、Gate 1 七项硬指标。
- 领域接口第一天冻结，基础设施按需引入。
- 创新集中在 I1～I6，不声称在基础模型/数据库/推理引擎/事件溯源/时态数据库理论上有创新。
- 任何「目前无人做过」的新颖性声明，必须先经查证再写入文档。
- **LifeOS 是主要矛盾，交互与载体是次要矛盾**：范围边界（1.1）的变更须走 ADR 并经决策层批准。
- 边界参数（1.2）与统计口径（3.2/4.4/4.5）的变更同样走 ADR。
- **「同一个它」的判定协议（1.3）变更等同于规格变更**：判定材料、阈值、流程任一变化都必须版本化并重跑受影响的层（v0.9.1 新增）。

## 16. 结论

LifeOS 的竞争力不来自使用了多少数据库或 Agent Framework，而来自是否能证明：同一个生命实例经过长期互动、模型升级和载体迁移之后，仍能以稳定、可信、可解释的方式保持「它还是它」。本规格把这一承诺拆解为：

- **3 条可证伪假设**（H1/H2/H3），由**三层判定框架**（S1 系统断言 / S2 行为探针 / S3 用户盲测）承接；
- **8 项量化指标（每项均给出可操作定义与数字来源）+ 6 项一票否决硬门**；
- **确定性/概率性职能表**：LLM 被四道锁限制在叶子位置；
- **3 个典型场景 + 4～5 基线对照 + 预注册统计规范与盲测设计**；
- **全开源技术栈 + 6 个经文献验证收窄后的创新点**（每项空白均注明学术与工程意义）；
- **4 阶段逐级授权交付**（1～2 → 6～10 → 12～20 → 24～40 人月），每阶段明确「输入数据 → 平台输出 → 验证对象」。

决策门前只证明「它还是它」。决策门后，再谈扩张。
