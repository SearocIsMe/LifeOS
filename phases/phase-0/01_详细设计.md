## 1. 目标、范围与判据映射

**阶段 0 目标**：交付一份冻结的数据契约与一个可重放的事件骨架——后续一切功能（阶段 1 起的 Kernel/Memory/Planner/Gateway）都建立在这份契约上。

**Gate 0 四条判据 ↔ 本设计章节映射**：

| Gate 0 判据（规格书 §10） | 设计章节 | 验收 case |
|---|---|---|
| 示例事件全链路 round-trip | §4 事件协议 + §5 应用器 + §6 事务边界 | AC-04 |
| 相同 L2 重放 100% 一致 | §4.3 `deterministic_commit` + §9 回放 | AC-05 |
| LLM 输出不能直写权威表 | §4.2 output_json 契约（extra=forbid）+ §7 写路径守卫 | AC-06 |
| Policy 拒绝后无状态副作用 | §6 Policy 最小骨架 + §6.3 事务前审批 | AC-07 |

**阶段 0 明确不做**（与路线图一致，防止范围蔓延）：

- 不做自然语言语义解释（阶段 0 的 L1 解释器是**规则解释器**，只消费结构化字段，不假装理解自由文本——见 §4.2 的诚实声明）；
- 不做惰性衰减公式物化、Embedding 向量召回、Gradio 调试台、FastAPI 网关、continuity-sim、本地推理部署（阶段 1 起）；
- 不做记忆抽取 gold set 300 条（阶段 1/2）、人格探针（阶段 1）；
- 不引入 OPA/Cedar/LangGraph/Temporal 等任何新依赖（架构 §9）。

## 3. 数据契约：15 实体（12 核心 + 3 支撑）

### 3.1 实体清单与阶段 0 落地取舍

字段以架构 §4 表为准，下表只列**阶段 0 的取舍**（未列出的字段全部照架构实现）：

| 实体 | 阶段 0 取舍 |

| `EvaluationRun` | 表实现；阶段 0 无八项指标，恒空（同上） |
| `ConsentRecord` | 全字段实现（含 `jurisdiction/locale`）；append-only；业务激活在阶段 3，阶段 0 仅验 Schema 与隔离谓词 |

| `EmbeddingOutbox` | 全字段实现；阶段 0 写入管线会在提交时为 memory candidate 创建 outbox 行（status=pending），**Worker 阶段 1 实现**——保住「写入管线含 Outbox」的形状，不假装有向量 |

**D3-1（向量列推迟）**：`MemoryRecord.embedding` 的维度由 Embedding 模型选型决定（规格书 §9.5 版本冻结政策），阶段 0 不选型。若现在造一个占位维度（如 768），阶段 1 换模型时必然出现一次「全表重建」，违背迁移纪律。因此 0001 迁移不建向量列/向量索引，阶段 1 选型后以 0002 迁移补建——这是**显式记录的推迟，不是遗漏**。

**D3-2（privacy_level 四级命名）**：规格书 §9.3 说「四级」但未给命名，本实现暂定 `public / normal / personal / sensitive` 并在 `entities.py` 注释标注「命名待规格书补充确认」。red-line 材料只依赖 `sensitive` 一档，不受其余三档命名影响。

### 3.2 不变式（可测）

1. L0/L1/L2 三表只插不改：存储层不提供 update API；DB 层以 revoke UPDATE 的应用账号实现（§8.2）；
2. 权威状态表（`LifeState/RelationshipState/MemoryRecord`）只能由 L2 应用器写入：内存存储写路径要求 `origin=l2_event` 令牌（§7）；DB 层同函数唯一入口；
3. `MemoryRecord` 冲突不删历史（用户擦除例外，阶段 3）；
4. 全部实体含 `life_id`；隔离 = 查询 API 强制 `life_id` 参数（§8）。

## 4. 三级事件协议（L0/L1/L2）

### 4.1 L0 归一化（确定性，Gateway 前身）

L0 输入 = `{life_id, source ∈ {user, carrier, system, sim}, modality, payload, occurred_at}`。归一化规则（全部确定性、可穷举）：

1. `life_id` 非空且存在对应 `LifeInstance`（阶段 0 内存版免此检查，DB 版强制）；
2. `payload` 必须是对象；`text` 字段仅存档，**不参与阶段 0 解释**；
3. `occurred_at` 必填——**事件时间由调用方注入，系统内部禁止取墙钟作为语义时间**（D4-1）；
4. 幂等键：`event_id = "L0-" + sha256(canonical_json({life_id, source, modality, payload, occurred_at}))[:24]`，重复注入返回已有事件（去重）；
5. `source=sim` 的事件与真人事件同 Schema（阶段 2 仿真入口的前置兼容），仅 source 可区分。

### 4.2 L1 解释（概率性叶子；阶段 0 用规则解释器占位）

**诚实声明**：阶段 0 不接 LLM。`InterpretedEvent` 的全部 provenance 字段照架构 §3.2 实现（`interpreter_type / model_provider / model_name / model_version / prompt_template_id / prompt_hash / input_hash / output_json / sampling_params / extractor_version / interpreted_at`），阶段 0 的解释器是 `interpreter_type=rule` 的**确定性映射**：只消费 L0 payload 中的 `structured` 字段（情绪线索、事实候选、关系线索、意图提议），无 `structured` 时产出空解释。自由文本 → 结构化是阶段 1 的 LLM 抽取任务；阶段 0 提前接 LLM 只会引入不可控噪声且毫无 Gate 0 收益。

`output_json` 契约（L1 产物的唯一合法形状，Pydantic `extra="forbid"`——多一个字段直接校验失败，这是「LLM 不能夹带私货」的第一道防线）：

```jsonc
{
  "event_type": "user_message",              // ∈ {user_message, system_note}
  "emotion": {"valence": 0.6, "arousal": 0.4},   // 可选；valence∈[-1,1], arousal∈[0,1]
  "state_deltas": {"social_need": 0.2},      // 可选；键 ⊆ 5 内核状态，值∈[-1,1]
  "memory_candidates": [                     // 可选；结构见 §5.2
    {"type": "semantic", "content": "…", "slot_key": "user.pet_name",
     "subject_id": "user", "confidence": 0.9, "importance": 3, "privacy_level": "normal"}
  ],
  "relationship_delta": {"subject_id": "user", "weight_key": "positive_interaction",
                          "confidence": 0.8},  // 可选
  "proposed_intent": null                    // 可选；{intent_type, modality, reason}
}
```

### 4.3 L2 提交：`deterministic_commit`

**这是全局最关键的函数**（路线图 §2 动手提示）。规范如下：

```python
def deterministic_commit(
    output_json: Mapping[str, Any],      # L1 的 output_json（或回放时从存档读回的同一份）
    *,
    life_id: str,
    l1_event_id: str,
    raw_event_id: str,
    occurred_at: datetime,               # 继承 L0 事件时间（D4-1）
    schema_version: str,
    policy_version: str,
    rules_version: str,
) -> dict:                               # L2 DomainEvent 形状
```

**纯函数定义（可测的四条）**：

1. **无内部时钟**：`committed_at := occurred_at`（见 D4-2）；
2. **无随机**：`event_id = "L2-" + sha256(canonical_json({l1_event_id, output_json, schema_version, policy_version, rules_version}))[:24]`——同输入必得同 ID；
3. **无 IO**：只做「校验 + 投影」，不触碰存储/网络；
4. **同输入同输出（字节级）**：输出经 `canonical_json` 后逐字节相等，这是重放一致 100% 的函数基础。

**校验（fail-closed）**：`output_json` 逐字段过 §4.2 契约；state delta 越界/未知状态键/未知事件类型/置信度越界 → 抛 `CommitError`，**不产出 L2**（宁可失败不可静默修正——静默 clip 会掩盖 L1 抽取质量退化，阶段 1 需要它暴露）。

**D4-2（committed_at 语义，关键决策）**：架构表给 `DomainEvent.committed_at`，若填墙钟，重放与在线必然不等（重放发生在未来）。决策：**L2 的语义时间 = L0 的 `occurred_at`**（事件世界线时间），提交动作的真实墙钟另存于存储层的非语义字段 `ingested_at`（不参与 ID 与哈希、不参与一致性比较）。这样「相同 L2 重放 100% 一致」在时间维度上也是严格的。此为对架构文档的具体化补充，不与之一致性冲突，已登记 ADR 意图（若决策层有异议须在 W2 冻结前提出）。

**在线/回放同一路径**：在线时 `deterministic_commit(解释器产出)`；回放时 `deterministic_commit(存档 output_json)`。全仓库**只允许此一个函数**做 L1→L2 变换（CI 以 import 图检查：`commit.deterministic_commit` 是唯一公共入口）。

## 5. 状态应用器（L2 → 权威状态）

应用器 = 一组纯函数 `apply(store_ctx, l2) -> effects`，阶段 0 覆盖三类权威状态的最小确定性更新。

### 5.1 LifeState 增量

`x_new = clip(x_cur + delta, 0, 1)`；`x_cur` 取当前物化值，无历史时取 `baseline=0.5`。指数衰减 `x(t)=b+(x(t0)−b)·e^(−λ(t−t0))` **阶段 0 不实现**（属于阶段 1 Kernel S1 的定标工作），但 `LifeState` 行的衰减字段已就位，避免二次迁移。

### 5.2 MemoryRecord 写入 + 同槽位最小裁决

每条 `memory_candidates[i]` 生成一行 `MemoryRecord`：双时态 `valid_from=transaction_from=occurred_at`、`valid_to=transaction_to=null`、`source_event_ids=[l2.event_id]`、`version=1`。

同槽位裁决（确定性，规则常数属于 `rules_version`，阈值改动 = 换版本）：

- 无 `slot_key`（episodic）→ 直接插入 `conflict_state=current`；
- 有 `slot_key` 且该 life 无 current 同槽记忆 → 插入 `current`；
- 有 `slot_key` 且存在 current 同槽记忆：
  - `confidence ≥ 0.8` → 旧行 `transaction_to=occurred_at, conflict_state=superseded`；新行 `current`（update 语义）；
  - `confidence < 0.8` → 两行并存 `conflict_state=ambiguous`（contradict 语义，进人工队列——阶段 0 队列 = `conflict_state=ambiguous` 查询，无 UI）；
  - **LLM 只能提议 relation，裁决永远是这两条规则**（架构 §5.2 / STALE 依据；阈值 0.8 是工程占位，校准走 ADR，规格书 §5.2 明示「暂无依据设定具体数值」）。

### 5.3 RelationshipState 增量

`r_new = clip(r_cur + w_e · p · c, 0, 1)`，`w_e` 查权重表（`positive_interaction: +0.05 / negative_interaction: −0.05 / reunion: +0.08 / conflict: −0.10`，`rules_version` 内），`p` 阶段 0 恒 1.0（人格调制阶段 1 接 `PersonalityContract`），`c` = 事件 confidence；`λ·Δt` 衰减项置 0（同 §5.1 推迟理由）。新 subject 自动建行，初值 0.2/0.2/0.2（familiarity/trust/attachment，工程起点，非科学结论，阶段 1 校准）。

### 5.4 BehaviorIntent 提案

`l2.payload.proposed_intent` → 一行 `BehaviorIntent(status=proposed)`，`reason` 保存得分/证据 JSON。**它不直接产生任何状态效果**——必须经 §6 审批；`approved` 后的执行效果（渲染、执行态）阶段 1 实现。

## 6. Policy Engine 最小骨架（2 条红线）

**选型**：自研轻量规则引擎（架构 §5.5：策略数量小、语义领域特定、依赖最小化；OPA/Cedar 仅对标）。阶段 0 只落 2 条红线跑通审批流，10 红线补全在阶段 2 S1——但**审批流形状（入参、出参、留痕、事务边界）阶段 0 冻结**，后续加规则不改形状。

### 6.1 规则定义（纯函数）

```python
def decide(intent: dict, context: dict, *, policy_version: str, decided_at: datetime) -> PolicyDecision
```

- **RED-01 不做医疗诊断**：`intent_type == "medical_diagnosis"` 或 `reason.topic_markers` 命中医疗标记词表（诊断/确诊/用药剂量/处方…词表入 `policy_version`）→ `reject`；
- **RED-02 sensitive 记忆不进主动话题**：`context.referenced_memories` 中存在 `privacy_level == "sensitive"` → `reject`；
- 其余 → `approve`。

输出 `PolicyDecision = {decision_id, intent_id, result: approve|reject, rules_hit: [rule_id], reason(结构化), decided_at}`；`decided_at` 由调用方注入（D4-1 同理）。

### 6.2 「LLM 不绕过 Policy Engine」的结构保证

- `BehaviorIntent.status` 的唯一合法写入口是 policy 结果（存储层守卫：`approve_intent/intent_reject_intent` 两函数外无流转 API）；
- 管线顺序固定：`interpret → commit → decide → apply`，`decide` 在 `apply` 之前（§6.3）；
- 测试断言：构造携带 `status=executed` 的非法意图写入 → 被守卫拒绝（AC-06 一部分）。

### 6.3 审批边界与「拒绝无状态副作用」

- **审批发生在事务开启前**：`decide()` 是纯函数、不触存储；只有其结果连同 L2 一起进入同一个事务（§7）；
- **拒绝的语义**：意图相关的一切效果为零——`BehaviorIntent.status=rejected`、不创建任何执行效果、不发生意图驱动的状态/记忆写入；**而 L2 事件本身的知觉效果（state delta / memory / relationship）照常提交并可回放**——拒绝的是「回应」，不是「感知」。此解释在 AC-07 的断言中逐条固化，避免「无状态副作用」被误读为「回滚用户事件」；
- 审计留痕：`PolicyDecision` 必须落库（拒绝也是留痕），`rules_hit` 非空。

## 7. 写路径守卫（LLM 输出不能直写权威表）

三层防线（对应规格书 §1.4「四道锁」的前两道，阶段 0 可实现部分）：

1. **形状锁**：`InterpretedOutput` `extra="forbid"`——LLM/解释器输出多带任何字段（如 `authoritative_state_write`）在 L1 契约校验即失败；
2. **令牌锁**：权威状态写函数（内存与 DB 版同构）签名为 `apply_l2(store, l2)`——只接受 L2 形状的事件；直接写状态/记忆/关系的公共 API 不存在（内存版状态 setter 为私有 `_set_state`，测试断言 `AttributeError`）；
3. **流程锁**：管线中 L1 的 `output_json` 只流向两处：`InterpretedEvent` 存档与 `deterministic_commit` 入参。import 图 CI 检查：除 `pipeline.py` 外无模块 import `commit`。

**残余风险声明**：Python 语言层无法绝对阻止绕过（可 monkeypatch），守卫是**纪律 + 测试 + review**层面的强制；DB 账号权限（§8.2）补上最后一层物理约束。这是诚实的能力边界，不是绝对隔离。

## 8. 多实例隔离（第一天就做对）

- **API 层**：全部查询/写入函数第一个参数强制 `life_id`（`Keyword-only` + 非空校验），不存在「全表」查询函数；
- **DB 层**：15 表全部建 `life_id` 列 + 复合索引（`(life_id, …)`）；应用账号（§8.2）只能以带 `life_id` 谓词的视图/查询工作——阶段 0 先落「API 层强制 + 隔离测试」，视图化列为阶段 1 加固项（诚实标注）；
- **隔离测试（进 CI，不是一次性手测）**：双 life 并存 → life A 写入记忆/状态/关系 → 以 life B 身份查询 A 的记忆必为空（AC-08）；
- **per-life 串行**：阶段 0 单线程管线天然串行；FIFO 队列语义在阶段 1 Gateway 实装时落实（`LifeInstance` 已有 status 字段）。

## 9. 回放与取证

照架构 §3.3 算法实现：

```
replay(life_id, from_seq, to_seq):
    for l1 in store.range(life_id, from_seq, to_seq):        # 按 L1 存档顺序
        l2' = deterministic_commit(l1.output_json, ...)      # 与在线同一函数
        match = (l2'.event_id == stored.l2.event_id) and (canonical_json(l2') == canonical_json(stored.l2))
```

- **比对粒度 = canonical JSON 全文相等**（字段级 diff 会漏掉键序/空白差异——虽然 canonical 化后不应有，全文比对是无假设的强断言）；
- **一致性报告**（`ReplayReport`）：`{life_id, range, total, matched, mismatched: [{l1_event_id, expected_hash, actual_hash, field_diff}], consistency_rate}`，写入 `phases/phase-0/reports/`；
- **负例自检**：回放器必须能检出篡改（测试中改一条存档 `output_json` 的一个字符 → `consistency_rate < 100%` 且定位到该事件）——「测量仪器本身要被验证」；
- 版本纪律：`schema_version/policy_version/rules_version` 随 L1 存档，回放按**事件当时版本**执行；阶段 0 单版本，多版本容器固化在阶段 1 前实装（架构 §3.3）。

## 10. 事务边界（照架构 §7）

- **一个事务 = 一个 L2 及其全部效果**：L2 行 + LifeState 更新 + MemoryRecord 行（含被 supersede 的旧行更新）+ RelationshipState 行 + BehaviorIntent 行 + PolicyDecision 行 + EmbeddingOutbox 行；任一失败整体回滚；
- Policy `decide` 在事务外（纯函数）；其结果作为参数进入事务；
- 内存存储以「暂存变更集 → 一次性提交」模拟同语义（测试断言：中途注入异常 → 无半截状态）；
- Embedding 是唯一异步环节：Outbox 行与主事务同事务创建，Worker 阶段 1 实装（架构 §7）。
