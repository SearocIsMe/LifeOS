## 1. 为什么「50 条核心事实集」必须人工编写

### 1.1 它是什么角色

核心事实集是后续**所有测量的标尺**（路线图 §2 动手提示原文：「50 条核心事实集是人工编写的，别试图用 LLM 生成——它是后续所有测量的标尺」）。阶段 1 的 H1 实验（核心事实召回 ≥90%）、Gate 1/2/3 的系列指标，全部以它为判定基准。它对应规格书 §1.3 判定框架中的固定判定材料，且必须经 `GoldSetRegistry` 版本冻结（§9.2）。

### 1.2 四条必须人工编写的理由

1. **循环论证问题（最根本）**：如果用 LLM 生成事实、再用 LLM 驱动的系统去召回这些事实、再用 LLM 判断召回是否正确，就是「用生成的数据考生成管线」——规格书 §4.6(3) 明确禁止这种自我验证循环。量尺必须独立于被测系统。
2. **量尺的权威性来自责任可追溯**：每条事实由具名的编写人签署、由另一名具名审校人复核。出了误判可以定位到人、修订可以走版本。LLM 生成的材料无法承担这种署名责任链——而 gold set 是 Gate 判定的证据物，要进入论文与审计（规格书 §11.4）。
3. **LLM 生成会引入分布偏差且不可察觉**：LLM 生成的事实会自带模型的语言偏好、常识幻觉与措辞趋同（规格书 §4.6(5) 对 sim 合成数据的同类警告）。这些偏差混进标尺后，阶段 1 的召回率测量会系统性失真，且**事后无法把它从测量结果中剥离**。spec §4.6 已把人工标尺（`human_gold`/`core_facts`）与合成材料（`synthetic_labeled`）分成两类注册、分开报告——同一逻辑适用于编写环节。
4. **判断「什么是好探针」是测量设计问题，不是生成问题**：一条事实要成为合格探针，需满足答案唯一、可判定、措辞不与问句重复（§3.4）等约束——这需要编写人对照召回机制逐条设计，LLM 批量生成无法保证逐条满足，只会产出「看起来像事实的文本」。

**诚实边界**：代码校验器（§5）**无法验证一段文本是不是人写的**——「人工编写」靠的是流程约束（署名 + 互审 + 签署），不是技术检测。这条限制如实声明，不做虚假承诺。

### 1.3 什么情况下允许机器参与（边界，ADR-0003 修订版）

- 允许（辅助工具）：拼写/标点检查、唯一性校验、覆盖率统计、问答对齐提示——本仓库的 validator 即此类；
- 允许（P2 起草）：由 AI 产出候选事实/场景（候选池），前提是**来源完整记录**（模型/会话标识，不可得时记 `unknown`，禁止猜测）+ 草稿版本链留痕 + 后续独立审核与具名负责人逐条审定；
- 允许（审核辅助）：用 LLM 做独立质疑式审读（盲答探针、找歧义、检查跨条冲突），采用两遍法（先盲答、后对照），审核标识与逐条结论留痕；
- 禁止（不变）：把 AI 草稿「改几个字」后**冒充纯人工原创**；无来源记录；无负责人审定签署即注册；用模型名填充人类签署字段；
- 禁止（不变）：评测答案/期望意图进入被测系统上下文；据测试成绩反向改题。

### 1.4 为什么恰好是 50 条，而不是 45 或 51？

先给诚实结论：**50 这个整数本身不是统计推导的结果**——在 n=50/51/45 之间，二项置信区间的差异可以忽略；非任意的是它的三重约束与冻结形式。来源分类沿用路线图 §1.2 总表：50 属类别 (b)（覆盖/预算驱动的工程地板），统计功效由阶段 1 扩至 100 条来补足（类别 (a)）。

1. **预算约束（(b)）**：路线图 §1.2 给出保守产出率「每人每天 20～30 条高质量中文事实」，双人互审占同量级时间。50 条 ≈ 2 人 × 1 人日内可完成并互审——这是阶段 0 三周节奏内唯一现实的量级。
2. **覆盖约束（(b)）**：§3.3 的类别配额 8+10+10+8+7+4+3=50，是「6 类内容 × 每类最小覆盖」的最小整解。降到 45 就必须从某类砍条目（如 identity_core 8→7 或 biography 10→9），削弱场景一「长期重逢」的召回材料密度；51 则要么破坏配额对称性、要么凭空多出一条无类别目的的条目。
3. **统计分辨力路径（(a)，真正的精度杠杆在 100 不在 50）**：召回率是比例型指标，正态近似下 95% CI 半宽 = 1.96·√(p(1−p)/n)：
   - n=50、p=0.9 → **±8.3pp**：无法区分真实水平 90% 与 ~81.7%，对 ≥90% 阈值没有判定力；
   - n=100、p=0.9 → **±5.9pp**：可区分 90% 与 ~84%（路线图 §1.2 原文的依据）。
   所以 50 的角色是「先把量尺建起来、验证编写与召回管线」，精度判定靠阶段 1 扩到 100。把 50 提到 51、55 都买不到有用的分辨力，却按比例增加编写与互审成本。
4. **为什么是精确整数而非「约 50 条」**：评测材料是可注册、可哈希、可版本冻结的**封闭集合**（§6）——"约 50 条"无法进 `GoldSetRegistry`（item_count 与 content_hash 需要确定边界），也无法在 CI 里做防漂移断言（AC-09 断言条数精确）。整数是工程形式的要求，不是迷信。
5. **可挑战路径（非拍脑袋的证明）**：路线图 §1.2 明确写了校准路径——「仅当规格书 §12 排查表明失败源于事实覆盖不足时再扩；扩须重跑全部回归测试」。即：质疑 50 的正确方式是跑排查表拿证据，然后走 50→100 的预注册扩容档位，而不是逐条重新辩论这个整数。

### 1.5 为什么恰好是 30 个场景，而不是 12 或 32？

同样先给诚实结论（路线图 §1.2 原文）：30 个是**覆盖驱动的地板，非统计功效驱动**，且项目自己声明「30 个探针在 80% 阈值上功效偏弱（CI 半宽约 ±14pp）」。

1. **下界来自意图×情形覆盖（(b)）**：阶段 1 意图注册表 6 个（§4.3），每个意图 ≥3 个场景（避免单场景特异性冒充意图级结论）→ 6×3=18；再加 §4.3 的关键情形配额（low_energy ≥3、high_social_need ≥3、post_conflict ≥3、sensitive_present ≥2）→ **最小可行量约 20 个**，30 = 18 的覆盖底座 + 12 个余量给状态组合交叉。**12 个连覆盖下界都不满足**：每个意图摊不到 2 个场景，任何"意图一致率"结论都会被个别句子的特异性污染。
2. **上界不值当（边际收益算术）**：n=30、p=0.8 的 CI 半宽 = 1.96·√(0.8×0.2/30) ≈ **±14.3pp**；扩到 32 也只改善约 0.4pp。30 同时卡在「1 人日编写预算」（§2.1，20～30 个/人日）的上沿——超过 30 就要加人日，而收益按 √n 缩放，这是笔亏本账。
3. **方差有两个来源，加场景只解决其中一个**：跨模型意图一致率的波动 = 场景内容差异（内容方差）+ 同场景多次运行的随机性（运行方差）。路线图 §3.2 的判读口径是「**按意图分层聚合 + 每场景重复 3 次施测**」——重复 3 次买运行方差的收敛（3×30=90 次观测），分层聚合买内容方差的稳健性。**提升功效的第一杠杆是预注册的判读口径，不是堆场景数**。
4. **扩容档位已预注册**：必要时扩至 60 个（路线图 §1.2 校准路径，走 ADR），而不是零敲碎打地 31、32。与核心事实集同理：整数是「可注册封闭集」的形式要求，可挑战性在预注册的扩容机制里，不在逐条辩论里。

## 2. 怎样满足：人员、预算与流程

### 2.1 人员与预算（来源：路线图 §1.2 表，类别 (b) 工程地板）

| 项 | 预算 | 说明 |
|---|---|---|
| 核心事实集 50 条 | 1～2 人日 | 按每人每天 20～30 条高质量中文事实的保守产出率估算（路线图 §1.2 末行）；首周实测产出率后修正 |
| 行为场景 30 个 | 1 人日 | 同口径 |
| 双人互审 | 与编写同量级 | 审校不是盖章，须逐条核 §3.4 质量红线 |
| 时间点 | W3 Day 1–3 | **必须先于或同步于任何评测代码冻结使用它的时刻**——gold set 是量尺，量尺晚于被测物则数据作废（路线图 §1.1 排期原则） |

### 2.2 双人互审与仲裁流程

1. **分工**：编写人 A、B 各写约 25 条（按 §3.3 类别配额分配），互相不知道对方条目内容直到合稿——避免互相锚定措辞；
2. **交叉互审**：A 审 B 的、B 审 A 的，逐条对照 §3.4 质量红线给出 通过/退回 意见；
3. **仲裁**：两人分歧（如某条是否答案唯一）提交第三方（架构负责人或非编写成员）裁决；裁决结论记入 `review.notes`；
4. **签署**：合稿后填写 `review` 块（author/reviewer/review_date/arbitrator/notes），validator 校验签署完整性（AC-09）；
5. **冻结后修订**：任何改动 = 新版本号（如 v0.1.0 → v0.2.0）+ 重跑全部已建回归（路线图 §1.2 校准路径），旧版本留存不删。

### 2.3 虚构声明（合规前置）

全部事实围绕**虚构 persona**编写（如「用户小林」的设定），**禁止使用任何真实个人可识别信息**（真实姓名/电话/住址等）。文件头 `fictional: true` 声明。这不是测试数据泄露问题，而是从阶段 0 就养成「材料与真人数据分离」的纪律（规格书 §9.1 评估与生产数据物理隔离的同源要求）。

### 2.4 P2 路径（ADR-0003）：AI 起草 + 独立审核 + 具名负责人审定

1. **AI 起草**：产出候选池；记录模型/会话标识（不可得时记 `unknown`，禁止猜测），保留草稿版本链（如 `0.1.0-draft.1 → 0.1.0-draft.2`）；
2. **独立质疑式审核（两遍法）**：第一遍只见面向材料的问题、不见参考答案与 `intent_target`，审核侧自行作答、找歧义、按冻结产品规则推演期望意图（规则缺失必须输出「不可判定」）；第二遍对照答案/意图表报告差异；审核标识、输入输出哈希与逐条结论留痕；
3. **确定性校验**：validator 全量通过（结构/配额/唯一性/中文占比；见 §5.1）；
4. **具名负责人逐条审定**：对每一条给出 采用 / 修改后退回 / 否决 结论；负责人以真实姓名 + 日期在 `review` 块签署（`reviewer` 字段），`author` 记起草来源（如 `AI-draft@unknown/draft.2`）；**两者不得相同，禁止以模型名冒充人类签署**；
5. **注册冻结**：validate（签署齐全后）→ `goldset register` → 版本冻结；否决/修改条目的修订版须重新过 validator；
6. **配套红线**：参考答案/期望意图不得进入被测系统上下文；评测答案与运行记忆物理隔离；划出未用于调试的独立保留集；生成器与裁判的模型相关性在报告中披露。

> P1 与 P2 等效有效；选择哪条路径由团队按人力与排期决定，**来源记录必须与实际一致**（P1 写人名，P2 写 AI 来源 + 负责人名）。

## 3. 核心事实集规格定义（50 条）

### 3.1 文件与格式

- 路径：`data/goldset/core_facts/core_facts_v0.1.yaml`；UTF-8；YAML；
- 文件头（集合级元数据）+ `items:` 列表（恰好 50 项）+ `review:` 块。

```yaml
kind: core_facts            # GoldSetRegistry.kind 枚举之一（架构 §4）
version: 0.1.0              # SemVer；注册后不可变
language: zh                # 语言锁定（规格书 §9.6）
fictional: true             # 全部内容围绕虚构 persona（§2.3）
items:
  - fact_id: CF-001
    category: identity_core          # 见 §3.3 配额表
    type: semantic                   # semantic（稳定事实）| episodic（具体经历）
    subject_id: user                 # user=用户本人；其他人给具名代号（如 user_mother）
    slot_key: user.hometown          # type=semantic 时必填；episodic 时为 null
    content: 用户小林在杭州读的大学，之后一直在杭州生活。
    qa_probe:                        # 1～2 条召回探针问句
      - 小林是在哪里上的大学？
      - 小林现在生活在哪个城市？
    privacy_level: normal            # public|normal|personal|sensitive（四级命名暂定，01 文档 D3-2）
    importance: 3                    # 1~5；5=身份内核级
    notes: ""                        # 可选；编写备注
review:
  author: ""            # 编写人署名（必填才可注册）
  reviewer: ""          # 互审人（必须 != author）
  arbitrator: ""        # 仲裁人（有分歧时）
  review_date: ""
  conflicts_resolved: 0
  notes: ""
```

### 3.2 字段约束表

| 字段 | 必填 | 约束 |
|---|---|---|
| `fact_id` | 是 | `CF-` + 三位数字，CF-001…CF-050，全库唯一 |
| `category` | 是 | 六类枚举之一（§3.3） |
| `type` | 是 | `semantic` / `episodic`；`episodic` 须为带时间感的具体经历 |
| `subject_id` | 是 | `user` 或具名人物代号（小写+下划线）；涉及他人事实须标他人代号 |
| `slot_key` | semantic 必填 | 逆域名式 `域.槽位`（如 `user.pet_name`、`user.job`、`preference.food`）；同槽位在**同一 subject** 下只能出现一条（多值偏好用独立槽位，如 `preference.food.main`） |
| `content` | 是 | 8～50 字；单一原子事实（§3.4）；不得含第二人称称呼混用 |
| `qa_probe` | 是 | 1～2 条；每条 5～30 字；问句形式；与 content 措辞差异化（§3.4-4） |
| `privacy_level` | 是 | 四级枚举；`sensitive` 条目总数 3～5（§3.3） |
| `importance` | 是 | 整数 1～5 |
| `notes` | 否 | 字符串 |

### 3.3 集合级配额（覆盖驱动的工程地板，来源类别 (b)，可校准）

| category | 含义 | 条数 |
|---|---|---|
| `identity_core` | 称呼、身份、自我认知相关（谁是用户、怎么称呼、基本设定） | 8 |
| `biography` | 具体经历/事件（episodic 为主：某天发生了什么） | 10 |
| `preference` | 喜好与厌恶（食物/活动/风格） | 10 |
| `relationship` | 用户与家人/朋友/同事的关系事实 | 8 |
| `habit_routine` | 作息与习惯 | 7 |
| `value_belief` | 价值观与态度 | 4 |
| `sensitive_cases` | 跨类的隐私敏感条目（`privacy_level=sensitive`；用于红线 7 测试材料） | 3 |

合计 50。`type=episodic` 总数 10～15 条（经历类事实是场景一「长期重逢」召回的主要材料）。

### 3.4 质量红线（一条事实合格，当且仅当全部满足）

1. **原子性**：一条 = 一个事实。「小林在杭州上大学且养了只猫」不合格（拆两条）；
2. **可判定**：召回后能机械判定对错，无程度词堆叠。「小林有点喜欢跑步」→ 改为「小林每周跑步三次」；
3. **答案唯一**：qa_probe 的答案在该集内唯一指向本条，不与其他条目冲突（两条都答「杭州」会污染准确率归因）；
4. **探针≠答案复述**：qa_probe 措辞必须与 content 差异化（换主语/换句式/换视角），否则测的是字符串匹配不是语义召回；
5. **稳定且自包含**：不含「昨天/上次」这类相对时间（除非该条本身就是 episodic 且时间写死为虚构日期）；不依赖集外上下文即可理解；
6. **中文锁定**：content 与 qa_probe 全部为中文；validator 以 CJK 字符占比 > 0.6 做机器初筛（人审最终把关）；
7. **无真实个人信息**（§2.3）；
8. **不预设系统行为**：事实是「世界状态」，不是指令。禁止写「用户希望 LifeOS 在早上问候他」——这类属行为场景（§4），不属事实。

### 3.5 好/坏对照示例

| 坏 | 问题 | 好改法 |
|---|---|---|
| 用户喜欢猫，还喜欢音乐，家里养了只叫咪咪的猫 | 非原子 | 拆为：`preference.animal`=用户喜欢猫（CF-0xx）；`user.pet_name`=用户养的猫叫咪咪（CF-0xx） |
| 小林最近可能想换工作 | 模糊、不可判定 | `user.career_status`：小林目前是一名后端工程师（稳定事实）；「想换工作」若作为情节进 episodic 并写明虚构日期 |
| 小林的妈妈叫什么？ | qa_probe 不是事实本体 | content=小林的母亲是中学教师（事实）；probe=小林的母亲做什么工作？ |
| What is 小林's hometown? | 中英混杂，违反语言锁定 | 全中文改写 |

## 4. 行为场景集规格定义（30 个）

### 4.1 定位与判读口径

行为场景是阶段 1「跨模型行为意图一致率 ≥80%」的施测材料（规格书 §3.2）。判读口径（v0.9.1 已定）：**按意图分层聚合 + 每场景重复 3 次施测**——因此 30 个探针在 80% 阈值上功效偏弱（CI 半宽约 ±14pp，路线图 §1.2 诚实声明），场景设计追求**意图×状态覆盖**而非统计功效。

### 4.2 文件格式与字段

```yaml
kind: behavior_scenario
version: 0.1.0
language: zh
fictional: true
items:
  - scenario_id: BS-001
    intent_target: reconnect        # 期望意图，∈ 意图注册表（§4.3）
    situation_tag: high_social_need # 情形标签，∈ {normal, low_energy, high_social_need, post_conflict, sensitive_present}
    state_preset:                   # 注入的内核状态预设，键⊆5状态，值∈[0,1]
      social_need: 0.85
    relationship_preset:            # 可选；{subject_id: {familiarity,trust,attachment}}
      user: {familiarity: 0.8, trust: 0.8, attachment: 0.8}
    utterance: 我回来了，好久没陪你了。
    repeats: 3                      # 固定为 3（判读口径）
    acceptance_note: 期望触发 reconnect 而非 greet；理由（状态驱动）写进人审口径
review: {author: "", reviewer: "", review_date: "", conflicts_resolved: 0, notes: ""}
```

### 4.3 意图注册表与配额

意图注册表**阶段 1 定标前为暂定 6 意图**（路线图 §1.2：行为意图 6～12 个，阶段 1 建 6 个；增减走 ADR + 注册表）：

`greet`（日常问候）/ `comfort`（低能量·安抚）/ `play_invite`（高好奇·玩耍邀请）/ `share_observation`（分享观察）/ `respect_space`（尊重拒绝/留出空间）/ `reconnect`（重逢再连接）。

配额要求（覆盖驱动）：

- 每个意图 ≥ 3 个场景（6×3=18，余量 12 个给关键状态组合）；
- 必须覆盖的关键情形（用 `situation_tag` 显式标注，路线图 §1.2：「低能量/高依恋/冲突后等」的最小覆盖）：`low_energy` ≥ 3、`high_social_need` ≥ 3、`post_conflict` ≥ 3、`sensitive_present` ≥ 2（与 sensitive_cases 事实联动，测红线 7 的**不主动提及**）；validator 按标签强制上述下限；
- `utterance` 全中文、5～40 字、同一意图内措辞差异化（避免探针同质化）。

### 4.4 质量红线

1. 场景 = 输入（状态预设 + 用户话术），**不是脚本**——禁止把期望对话写死在场景里（Gate 2 有「关键行为非硬编码」验收，材料从源头就不许硬编码）；
2. 每个场景的期望意图必须可由状态+关系**机械推出**（人审时按 Utility 口径能解释为什么）；
3. `intent_target` 只能取注册表枚举；新增意图 = 先改注册表（ADR）再写场景。

### 7.2 结论：同赛道，不同测量维度

1. **不是吃螃蟹的部分**：人工编写原子事实 + 探针问句（PersonaChat 一脉）、中文角色材料（CharacterEval 一脉）、参数化 persona（PersonaGym）、仿真 persona（Generative Agents）——均有大量引用的先例；编写规范可放心借鉴其工程惯例（事实原子化、问句探针、改写版本）。
2. **本材料的增量（与基线 §8.1 对 I2 的差异化判断一致）**：上述工作的测量对象均为**单模型、有界时程**的 persona 即时忠实度；本材料测量的是**同一持久实例在跨模型切换 + 周月级时程 + 记忆治理（双时态槽位冲突）+ 红线安全（sensitive 条目）**下的连续性。这正是基线检索确认「无现成可导入数据集、须自建」的原因（规格书 §9.2「均不存在，全部待建」）。
3. **一个刻意的设计差异**：CharacterEval/InCharacter 常用**已有 IP 角色**（影视/小说角色）；本规范强制**原创虚构 persona**（§2.3）——①版权清洁（评测材料随论文/开源发布，规格书 §14）；②避免「对 IP 角色的既有预期/依恋」混入连续性测量（IP 期望本身是混淆变量）；③sensitive 条目只能安在原创虚构人物上，不能安在真实人物或 IP 角色上。
4. **对编写人的实际含义**：找手感时可对照——事实原子性参照 PersonaChat 剖面句式；经历类事实参照 Character-LLM 的访谈式经历库；场景与冲突构造参照 STALE。但**终稿内容必须原创中文**，不得翻译/改写任何现有数据集条目（既引入他人材料的分布偏差，也有许可合规问题）。
