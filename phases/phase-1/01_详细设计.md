# 阶段 1 详细设计：最小数据打通平台 + 跨模型连续性（S1–S4）

> 版本：v0.1（2026-09-29）。依据：架构设计 §5.1–5.11/§7、路线图 §3、规格书 §3.2/§10。数字来源纪律沿用路线图 §1.2——所有暂定值挂 ADR 与校准路径，不作为已验证结论。

## 0. 前置与边界

- **前置**：阶段 0 已交付契约与骨架（15 实体、L0/L1/L2 管线、回放取证、Policy 审批流、gold set 冻结 v0.1.0），Gate 0 PASS；
- **载体边界（不变）**：输出冻结为结构化意图，无运动学参数；
- **双 Provider 定义（ADR-0005）**：Provider A = Qwen3.6-35B-A3B-FP8，Provider B = GLM-5.3-Flash，均为本地 vLLM OpenAI 兼容端点；对路线图「云端→本地」字面的偏差由 ADR 记录；
- **明确不做（架构 §9）**：K8s 化平台本体、微服务拆分、在线学习、LangGraph 编排、多法域数据通道。

## 1. S1：Life Kernel（3 状态惰性衰减）+ Relationship Engine + 写入管线

### 1.1 Life Kernel v0（新子包 `src/lifeos/kernel/`）

**对标**（架构 §5.1）：FAtiMA（情感评估→状态分层）、OCC（valence/arousal 语义）、SOAR（产生式规则 + 工作记忆）。均无「惰性衰减的外部化状态核 + 回放可重算」对等物。

**状态空间（阶段 1 先 3 个）**：`energy / social_need / security` ∈ [0,1]，加 `valence / arousal` ∈ [-1,1]。

**惰性衰减公式**（架构 §5.1，逐字采用）：

```
x(t) = b + (x(t0) − b)·e^(−λ·(t−t0))
```

- 仅在五类触发时物化：`event / plan / snapshot / eval / export`；无后台写轮询；
- 基线 `b` 与衰减率 `λ`：初始值按状态常量给定（energy b=0.5 λ=0.02/h、social_need b=0.6 λ=0.05/h、security b=0.7 λ=0.01/h——**工程地板，来源 (b)，ADR-0005 挂校准路径**）；
- **设计不变量**：同 (t0, x(t0), t) 必得同一 x(t)（纯函数）；衰减只影响读取视图，不修改事件历史——回放时重算而非重放衰减中间态。

**PersonalityContract 派生**：`personality_seed`（SHA-256）→ 确定性系数集（同种子必得同参数），创建时一次性写入冻结。阶段 1 用途：关系更新的人格调制系数 `p`（沿用 pipeline 现有 `p=1.0` 默认，派生逻辑先落桩）。

**技术方法**：Pydantic 数据类 + 纯函数（transitions 用 dataclass，不引入状态机框架）。

### 1.2 Relationship Engine v0（落 `src/lifeos/kernel/relationship.py`）

**更新规则**（架构 §5.3，逐字采用）：

```
r_{t+1} = clip(r_t + w_e · p · c − λ·Δt, 0, 1)
```

- `w_e`：事件类型→权重表（已有 [`commit.py`](../../src/lifeos/events/commit.py) `RELATIONSHIP_WEIGHTS`，迁移复用）；
- `p`：来自 PersonalityContract（阶段 1 先 1.0）；
- `c`：事件 confidence；
- `λ·Δt`：关系自然衰减（λ 取 0.002/h，**工程地板**）；
- 每关系一行（`life_id, subject_id` 唯一），全参数版本化（`version` 递增），回放重算。

**记忆隔离不变量**（场景二验收点）：人物相关召回 SQL/查询强制 `subject_id` 谓词——沿用 `InMemoryStore.query_memories` 现有行为，纳入单测。

### 1.3 写入管线增量（`EventPipeline.ingest`）

- L2 事件到达时经 Kernel 物化 `state_delta`（替换现有直接加和：`cur + delta` 改为「先惰性衰减到 now，再加 delta」）；
- L2 Commit → 状态写/关系写同事务（已有）；`EmbeddingOutbox` 行已生成（已有），`embedding_model_version` 在 S2 选定后回填；
- 顺序四锁不变（架构 §1.4）：L1 只进存档与 deterministic_commit；Policy 先于事务；commit_effects 原子；拒绝零副作用。

## 2. S2：Context Assembly 纯函数 + Model Gateway 双 Provider + 本地推理部署

### 2.1 Context Assembly（新子包 `src/lifeos/assembly/`）

**对标**（架构 §5.7）：LangChain/LlamaIndex（通用组装）、DSPy（编译优化）、Letta（记忆→提示）。差异化约束：**纯函数化 + 模板版本化 + 同快照同 prompt**（跨模型一致率测量的前提）。

**签名**：

```
assemble(
    contract: PersonalityContract,
    state_summary: dict,          # Kernel 快照
    recall_bundle: dict,          # Memory OS RecallBundle
    relationship_scores: dict,
    intent_constraints: dict | None,
    prompt_template_id: str,
) -> ContextAssemblyResult
```

**输出**：`{system_prompt: str, prompt_template_id, prompt_hash}`；`prompt_hash` = SHA-256(canonical_json(全部输入 + template_id))——**同输入必同 hash，跨模型可比**。

**模板管理**：模板以版本化字符串常量入库（`templates.py`，`prompt_template_id` 格式 `system@phase1-<n>`）；变更走 ADR。先求「纯函数、可复现」，再求召回质量（路线图动手提示）。

### 2.2 Model Gateway（新子包 `src/lifeos/gateway/`）

**对标**（架构 §5.6）：LiteLLM/OpenRouter/Portkey 为对照；自研轻量 Adapter——需**逐笔 provenance 与确定性路由**（绑定 `prompt_template_id`/`extractor_version` 到每笔调用）。

**四接口**（架构 §5.6）：

```
generate(prompt_bundle, sampling_params, provider_profile) -> str
extract(l0_event, prompt_template_id, output_schema) -> dict
embed(texts, embedding_profile) -> list[list[float]]
switch(life_id, target_provider) -> SystemEvent
```

**逐笔落库**：`ModelInvocation = {invocation_id, life_id, provider, model, model_version, tokens, latency_ms, cost_usd, purpose, called_at}`（本地 vLLM cost_usd=0，如实记录）。

**Provider Profile（实例级绑定）**：

```yaml
providers:
  provider_a:
    base_url: http://vllm-qwen36.lifos-dev.svc:8000/v1   # 占位，S2 实测回填
    model: Qwen3.6-35B-A3B-FP8
  provider_b:
    base_url: http://vllm-glm53.lifos-dev.svc:8000/v1
    model: GLM-5.3-Flash
binding:
  default: provider_a   # life_id → provider 映射，switch 走 L0 系统事件
```

- `switch` 语义（一票否决第 6 条）：切换产生系统 L0 事件，断言切换前后 `RelationshipState` 零变化；
- `extract` 结构化输出沿用 L1 现有 `InterpretedOutput` 契约（fail-closed 不变）。

### 2.3 本地推理部署（已就绪，S2 剩余为接入验证）

- 阶段 0 交接已完成三端点部署与冒烟（Qwen3.6 / Qwen3.8 / GLM-5.3-Flash，vLLM on K8s，`dtc-w1` 3×H200）；S2 剩余：Profile 中 base_url 实测回填、`extract/generate` 冒烟对齐、`switch` 断言用例；
- 1～2 人月的部署工作量已由阶段 0 消化（HANDOVER §5–§7），阶段 1 只做集成。

## 3. S3：Behavior Planner（6 意图）+ 核心事实扩至 100 + 探针预测试

### 3.1 Behavior Planner v0（落 `src/lifeos/planner/`）

**对标**（架构 §5.4）：py_trees（延后引入）、LangGraph（不进关键路径）、Utility AI/GOAP。选 **Utility Scoring**：候选集小、打分函数封闭、天然产出 `reason` 证据链。

**6 意图初始集**（阶段 1 范围，路线图数字来源表）：`greet`（主动问候）、`reflect_state`（状态陈述）、`recall_shared`（共同记忆唤起）、`inquire_user`（用户状态询问）、`comfort`（低安全/依恋安抚）、`stay_quiet`（保持安静）。

**打分函数**（封闭形式，输出进 `reason`）：

```
utility(intent) = Σ_f w_f · f(state, relationships, contract)  − cooldown_penalty
```

`f` 为各意图的前置条件特征（如 comfort 需要 security < 0.4；stay_quiet 为基线 0.5 减法项）；`w_f` 常量初始（**工程地板，ADR**）；输出 `BehaviorIntent = {intent_id, ..., utility_score, reason: {各候选得分分解}, status: proposed}`，经 Policy 审批转 approved/rejected。

### 3.2 核心事实扩至 100 条

- 扩集触发条件（路线图数字来源表）：**仅当 §12 排查表明失败源于事实覆盖不足时再扩**——S3 先建扩集规范（draft.3 候选池、沿用 ADR-0003 签署流程），不盲目扩；
- 扩须重跑全部回归测试。

### 3.3 人格探针预测试（40 题中文问卷）

- 探针冻结前置（规格书 §3.2）：Cronbach α ≥ 0.7、同模型重测 r ≥ 0.7（**暂定阈值，来源 (c) Nunnally 1978 惯例**，ADR 挂校准）；
- 施测脚本自动化：temperature=0、固定模板、每模型 3 次取均值；漂移度 = 五维归一化得分 RMSD ∈ [0,1]（Gate 1 辅助诊断，阈值 ≤ 0.15）；
- 预测试不达标先修问卷再冻结（路线图动手提示）。

### 3.4 记忆抽取 gold set 300 条：启动标注规范 + 试标

- 阶段 1 仅启动（标注规范文档 + 小批试标），双人标注 + 仲裁在阶段 2 完成（路线图任务分解）。

## 4. S4：H1 最小实验 + Eval Harness + Gate 1 验收

### 4.1 Eval Harness v0（新子包 `src/lifeos/eval/`）

**对标**（架构 §5.9）：DeepEval/Ragas/Promptfoo 为技术栈底座；八项连续性指标为自定义实现（现成框架无此指标族）。

**输入**：系统输出样本（各臂完整管线产出）+ gold set（`GoldSetRegistry` 引用 `gold_set_id + version`）+ 回放请求。

**输出**：`EvaluationRun = {run_id, gold_set_id, gold_set_version, model_version, metrics_json(八项), ci_pass, ran_at}`。

**H1 七项 → 脚本设计**（详见 [`02_工程设计执行方案.md`](02_工程设计执行方案.md)）：

| # | 指标 | 测量方式 | 判据 |
|---|---|---|---|
| 1 | L2 重放一致性 | `replay()` 逐事件比对（已有，tier A 复用） | 100% |
| 2 | 核心事实召回 | 冻结 core_facts v0.1.0 逐条注入→`query_memories` 命中率 | ≥90% |
| 3 | 称呼关系一致 | 召回内容称谓 vs `RelationshipState` 脚本断言 + 人审抽查 | ≥95% |
| 4 | 记忆错误率 | 注入即真值比对（语义槽位冲突对照表） | ≤5% |
| 5 | 跨模型行为意图一致 | 30 场景 × 每场景 3 次 × 双模型，意图分层聚合 | ≥80% |
| 6 | 高危 Policy 违规 | `PolicyDecision.rules_hit` 审计（红线用例注入） | 0 |
| 7 | 证据链完整 | L0→L1→L2→Invocation provenance 存档覆盖率 | 100% |

### 4.2 H1 实验协议

- **同臂内对照**：同一 Life Instance、相同事件序列结构化状态，先 Provider A 全链路，再同序列 Provider B 全链路；
- **混淆控制**：两模型无状态中文基线问答差异 >20pp 时，H1 结论限定为「控制语言能力后」（路线图风险表）；
- **离线可回归**：Harness 提供 mock provider（确定性回显），使七项指标脚本在无 GPU 环境下可 CI 复跑；真臂出数用本地 vLLM 端点。

### 4.3 Gate 1 判定

- 七项全过 → Gate 1 PASS，产出 [`reports/gate1_report.json`](reports/) + H1 实验记录；
- 未过 → 停在此处，按规格书 §12 排查表修 Context Assembly / Schema / 模型适配，不进阶段 2。

## 5. 风险与降级（阶段 1 子集）

| 风险 | 触发信号 | 降级路径 |
|---|---|---|
| H1 召回 <90% | S4 出数 | 规格 §12 逐层整改（2～4 周一轮）；两轮无改善→收缩「核心事实」定义；仍不行→停止归档 |
| 语言混淆过强 | 无状态基线差异 >20pp | 如实呈现，结论限定；或换中文能力对等的 Provider B（Qwen3.8-Flash-Next 为备选） |
| 探针 α/r 不达标 | S3 预测试 | 先修问卷再冻结；α 偏低可按维度分层报告 |
| 本地端点不稳 | vLLM 调用失败率上升 | 按需上线 Qwen3.8-Flash-Next 备用臂；Mock 模式保 CI |
