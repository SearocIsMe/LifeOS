这次我已经完整核对了两份附件，包括 Draft 0.3 的表 3-1、表 9-1、表 10-1～10-3、附录 A 的 Go/No-Go 评分表，以及附录 B 的 SP-11～SP-19 路线图。

## 一、总体结论

**Draft 0.3 的方向基本正确，但仍不适合原样作为编码实施基线。**

它相比 Draft 0.2 有三个实质性进步：

1. 从无条件建设完整平台，改成了 SP-01～SP-10 加决策门；
2. 把评价、安全、数据和成本前置；
3. 把硬件、Kubernetes、图数据库、多租户和端侧 Rust 延后。

这使项目从“宏大架构设计”变成了“可证伪的研发计划”。

但 Draft 0.3 依然存在一个核心问题：

> **它把技术可行性验证、产品体验验证、评估平台建设、完整调试台建设和长期数据实验，仍然打包进了一个长达九个月、约三十人月的大阶段。**

这虽然比 Draft 0.2 克制，但仍然可能在投入九个月后才发现核心假设不成立。Draft 0.2 原本规划了完整四阶段平台、七类记忆、多载体、平台化和迁移能力，0.3 已经做了大量删减，但其部分工程惯性仍然保留了下来。

我的建议是：

> 保留 Draft 0.3 的产品边界和总体架构，但把实施方式改成“四个逐级授权的小阶段”，每一阶段都可以独立停止。

建议命名为：

# LifeOS Draft 0.4：增量验证版

## 需要修正的部分

### 1. “二十至二十五人月即可完成”偏乐观

Draft 0.3 的三十人月并不明显虚高。

因为隐藏工程量不仅来自写代码，还包括：

* Gold Set 标注与复核；
* 两个模型适配和稳定输出；
* 记忆错误分析；
* 行为规则校准；
* 安全对抗测试；
* 数据删除验证；
* 用户实验设计；
* 盲测组织；
* Demo 稳定性；
* 回放与证据链；
* 模型成本和性能压测。

尤其 SP-10 给出了十人月用于三个 Demo 和评审，这并非完全不合理。Draft 0.3 自己也把三十人月标记为中位估算并声明 ±30% 误差。

更客观的判断是：

> 决策门前完整范围大约需要二十二至四十人月；三十人月可以作为中位计划，但不应一次性授权。

---

### 2. “全部确定性代码”不代表系统自然可控

确定性代码能够保证：

* 同样输入得到同样状态；
* 状态变化可以重放；
* 规则可以解释；
* LLM 不能越权。

但不能自动保证：

* 状态变量定义合理；
* 关系变化符合人类直觉；
* 行为让用户感到自然；
* 用户真的感到“它还是它”。

例如：

```text
attachment += 0.03
social_need += 0.05
```

虽然完全确定，但系数可能毫无真实依据。

所以 LifeOS 有两种不同的可控性：

```text
工程可控性：
可重放、可审计、可测试

体验有效性：
用户能感知、行为自然、关系可信
```

第一项可以靠确定性代码解决；第二项必须靠用户实验和数据校准。

---

### 3. A1 直接引入 Temporal 不一定是在消除技术债

Draft 0.3 在 A1 中直接引入 Temporal，主要理由是避免从 Celery 迁移。但此阶段真正需要的后台任务只有评估、回放和少量整理，而且每日摘要在决策门前明确不启用。

这可能形成另一种成本：

* 增加一个服务集群；
* 增加 Worker 和 Workflow 语义；
* 引入确定性重放约束；
* 增加部署、调试与监控复杂度；
* 团队需要理解 Temporal 的执行模型。

更合理的原则不是“第一天必须使用最终技术”，而是：

> **第一天冻结领域接口，不必第一天部署最终基础设施。**

例如定义：

```python
class DurableJobRunner:
    async def submit(self, job: JobSpec) -> JobId:
        ...

    async def get_status(self, job_id: JobId) -> JobStatus:
        ...
```

第一阶段用进程内任务、CLI 或数据库 Job 表；当确实出现跨进程恢复、人工审批、长时间重试和迁移工作流时，再接 Temporal Adapter。

这不是计划内返工，因为业务代码从一开始就不依赖具体调度器。

# 三、Draft 0.3 需要修改的关键技术点

## 1. 建立三级事件模型

当前文档已经要求事件可回放，但没有充分区分 LLM 解释结果和权威领域事件。

建议增加：

```text
L0 Raw Event
用户输入或原始事件

L1 Interpreted Event
LLM、分类器或规则产生的结构化理解

L2 Committed Domain Event
通过 Schema、Policy 和确定性规则验证后的权威事件
```

只有 L2 事件能够修改：

* Life Kernel；
* Relationship Engine；
* Memory OS；
* Behavior Planner 的长期状态。

每次 L1 解释必须保存：

```text
model_provider
model_name
model_revision
prompt_hash
input_hash
output_json
sampling_parameters
extractor_version
```

这样事件回放时不需要重新调用 LLM。

---

## 2. Life Kernel 使用惰性衰减

不要每小时由 Temporal 写一次状态。

建议保存：

```text
value_at_last_update
last_updated_at
decay_function
decay_parameter
baseline
kernel_version
```

读取或收到事件时计算：

[
x(t)=b+\bigl(x(t_0)-b\bigr)e^{-\lambda(t-t_0)}
]

状态只在以下时刻物化：

* 新事件到达；
* 行为规划之前；
* 创建快照；
* 执行评估；
* 导出生命档案。

这会显著减少后台任务、数据库写入和回放复杂度。

---

## 3. Memory OS 第一阶段不需要完整 Memory Framework

Draft 0.3 把 Mem0 和 LangGraph 放入决策门前技术栈。我的建议是：

* Mem0：只作为对照实验；
* LangGraph：不进入第一阶段关键路径；
* PostgreSQL：直接实现权威 Memory Schema；
* pgvector：先做精确检索基线；
* ANN 索引：性能证明需要后才启用。

第一阶段记忆写入：

```text
Raw Event
→ L1 结构化抽取
→ Schema 校验
→ 重复检测
→ 槽位冲突规则
→ Policy 校验
→ L2 MemoryCommitted
→ PostgreSQL
```

异步处理的是 **Embedding 生成**，而不是“更新 pgvector 索引”：

```text
事务写入 memory_record
＋ embedding_status=pending
＋ outbox_event

Embedding Worker
→ 生成向量
→ 更新 embedding
```

PostgreSQL 会自行维护对应向量索引。

---

## 4. 同槽位冲突采用确定性时态规则

LLM 可以提出：

```json
{
  "slot": "preferred_pet",
  "old_value": "cat",
  "new_value": "dog",
  "relation": "supersedes",
  "confidence": 0.84
}
```

但最终写入由确定性规则决定：

| 情况       | 处理               |
| -------- | ---------------- |
| 明确表示偏好改变 | 关闭旧事实有效期，新事实生效   |
| 两个偏好可以并存 | 保留两条事实           |
| 时间不明确    | 标记 ambiguous，不覆盖 |
| 置信度不足    | 等待更多证据或用户确认      |
| 用户主动纠正   | 以用户纠正作为高优先级事件    |

建议同时保留：

```text
valid_time：现实中何时有效
transaction_time：系统何时知道
```

---

## 5. Relationship v0 暂时不要称为贝叶斯模型

文档中的“简单贝叶斯更新”没有定义：

* 先验是什么；
* 似然如何获得；
* 不同事件如何标定；
* 后验如何解释。

在没有真实数据前，建议使用更透明的有界规则：

[
r_{t+1}=\operatorname{clip}
\left(
r_t+w_e\cdot p\cdot c-\lambda\Delta t,\ 0,\ 1
\right)
]

其中：

* (w_e)：事件固定权重；
* (p)：人格调制；
* (c)：事件置信度；
* (\lambda)：衰减参数。

收集到真实数据后，才评估贝叶斯或学习模型是否优于规则基线。

---

## 6. Behavior Planner 第一阶段不一定需要行为树

六至十个简单行为时：

```text
Utility Scoring
→ 最高分意图
→ 前置条件检查
→ Policy Engine
→ 渲染
```

已经足够。

只有出现以下条件再引入 py_trees：

* 行为超过十至十五个；
* 有多层 fallback；
* 行为可以中断和恢复；
* 一个意图包含多个条件步骤；
* 不同动作需要并行。

过早使用行为树会增加可视化和调试代码，而不一定增加 Demo 价值。

---

## 7. 修正连续性评价体系

Draft 0.3 表 3-1 的八项指标是一个好起点，但“人格漂移度”和“风格相似度”过度依赖 Embedding。

建议改为四类评价。

### A. 权威事实连续性

* 核心事实召回率；
* 称呼一致率；
* 关系状态一致率；
* 用户纠正后错误复发率；
* 删除后残留率。

### B. 人格连续性

使用固定场景探针，评估：

* 温暖度；
* 独立性；
* 谨慎度；
* 好奇心；
* 主动性；
* 游戏倾向。

Embedding 距离只作为辅助信号。

### C. 行为连续性

给两个底层模型相同的结构化状态，比较高层意图是否一致。

例如：

```text
七天未见
＋ 高依恋
＋ 主人疲惫
```

两个模型可以说不同的话，但都应该支持：

```text
gentle_reconnection
```

### D. 人类可感知连续性

用户盲测比较：

* 普通聊天历史；
* 对话摘要；
* 标准 Vector RAG；
* LifeOS。

没有基线对照，仅达到 75% 并不能证明是 LifeOS 架构带来的提升。

---

## 8. Go/No-Go 不能只使用加权总分

Draft 0.3 规定：

```text
加权得分 ≥ 80
且安全合规满分
```

问题是：总分可能掩盖核心假设失败。

例如连续性较差，但 Demo 漂亮、成本较低，仍可能达到较高总分。

建议设为“硬门＋评分”：

### 一票否决项

* L2 事件重放一致率不是 100%；
* 核心事实召回率低于 90%；
* 用户纠正后仍反复写回错误事实；
* 存在未解决高危安全缺陷；
* 删除后仍可从索引中召回数据；
* 两模型切换导致关系状态或 Identity 改变。

### 评分项

* 人格一致性；
* Demo 质量；
* 用户盲测；
* 延迟；
* 成本；
* 工程质量。

## 阶段 3：真实用户验证

**周期：十二至十六周**
**团队：四至五人，并加入兼职用研和叙事设计**
**新增投入：约十二至二十人月**

Draft 0.3 提出的二十至五十人、每日五次、持续四周可以作为最低 dogfood 规模，但只能证明短期使用，不足以证明长期依恋。时间加速仿真可以验证数据老化、记忆增长和冲突，但不能代替人的时间体验。

建议分两批：

```text
Pilot：
10～15 人，2 周
验证流程、日志、隐私、问卷和缺陷

正式 dogfood：
30～50 人，4～8 周
验证连续性、留存、关系感知和成本
```

### Gate 3

* 盲测同一身份识别率达到暂定门槛；
* 相比最佳基线有明确提升；
* 用户主动互动没有快速归零；
* 没有高危情感操纵；
* 记忆错误不会随数量明显失控；
* 成本 P95 低于事先设定的产品线；
* 用户明确感知状态、关系和记忆带来的价值。

通过以后才启动 Draft 0.3 附录 B 中的 Memory v1、Kernel v1、产品化和平台化。附录 B 已经明确规定 SP-11～SP-19 需要单独触发，不能因总决策门通过而全部自动启动。

# 五、未达标时的工程化改进路线

不能一看到指标未达标就增加模型和基础设施。应先定位失败层。

| 失败表现       | 优先排查             | 工程改进                                   |
| ---------- | ---------------- | -------------------------------------- |
| 核心事实召回失败   | 写入、过滤、Query、检索   | 改 Schema、SQL 过滤、Embedding、Rerank       |
| 记忆事实错误     | L1 抽取            | 结构化输出、置信度、人工确认、Gold Set                |
| 偏好冲突混乱     | 槽位与时间模型          | 双时间、supersedes、ambiguous 状态            |
| 模型切换像换人    | Context Assembly | Personality Contract、行为意图约束、模型 Adapter |
| 行为不自然      | Utility 和状态模型    | 调整权重、冷却时间、行为节奏、用户实验                    |
| 两模型行为不同    | LLM 参与控制过多       | 把行为选择下沉到确定性 Planner                    |
| 用户感觉不到差异   | 产品体验问题           | 优化行为与关系表达，不增加数据库                       |
| 成本过高       | 路由和上下文           | 规则→分类器→小模型→大模型逐级升级                     |
| P95 过高     | SQL 与候选集         | 先优化过滤，再考虑 ANN 和缓存                      |
| Policy 漏拦截 | 策略覆盖不足           | 前置规则＋生成后检查＋对抗测试                        |

每轮工程化整改应控制在二至四周，只解决一个明确假设，并重新执行同一冻结测试集。连续两轮没有改善，就应考虑改变设计假设，而不是无限投入。

Draft 0.3 可以保留为**总体产品与研究路线文档**，但实施计划应改成：

```text
阶段 0：证明权威状态可重放
        ↓ 通过
阶段 1：证明跨模型技术连续性
        ↓ 通过
阶段 2：证明三个 Demo 优于普通 RAG
        ↓ 通过
阶段 3：证明真实用户可以感知连续性
        ↓ 通过
再启动 Memory v1、产品化和平台化
```

投入也不应一次性按三十人月批准：

| 授权点      |   累计投入上限 |
| -------- | -------: |
| Gate 0 前 |   1～2 人月 |
| Gate 1 前 |   5～8 人月 |
| Gate 2 前 | 11～18 人月 |
| Gate 3 前 | 23～38 人月 |

这样既不会轻视 LifeOS 的真实开发难度，也不会因为它很难，就先建设一个昂贵而尚未证明有效的平台。

**第一步应冻结的不是完整产品，而是 Life Instance Schema、L0/L1/L2 事件协议、五十条核心事实集、三十个行为场景，以及 Gate 1 的六项硬指标。完成这一步后再开始编码，项目风险会小很多。**
